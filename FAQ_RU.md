## Область применения проекта и модель выполнения

### Что такое Easy G-Code Plot?

Easy G-Code Plot — это редактор ЧПУ, детерминированный исполнитель программ, анализатор, построитель траекторий и экспортёр для токарных и фрезерных программ FANUC и фрезерных программ SINUMERIK 840D. Поддержка native SINUMERIK включает CAM-траектории с индексированием 3+2 и непрерывной пятиосевой обработкой на настроенных поворотных профилях; ISO Dialect M также поддерживается в описанном подмножестве.

Проверялись CAM-программы из Autodesk Fusion 360 и Siemens NX 2312, сформированные постпроцессорами для SINUMERIK 840D и FANUC. Проверенное покрытие относится к описанным в FAQ командам и настроенным кинематикам.

Проект имеет две пользовательские точки входа:

- настольный GUI на PyQt6;
- автономный исполняемый файл CLI.

Оба используют одно и то же ядро ЧПУ и один и тот же рассчитанный результат `ExecutionResult`. GUI не является вторым интерпретатором, а CLI не содержит собственного упрощённого парсера.

### Как устроен основной поток обработки данных?

Основной поток данных:

```text
G-code source
    |
    `--> Parser / controller frontend
           |- native Cython parser
           `- per-block Python fallback where required
                |
                v
             Program / AST
                |
                v
          Program tool setup
          (AST operation hints, library lookup, manual overrides)
                |- source comments / dimensions: Cython scanner
                `- Python scanner fallback
                |
                v
          CNC execution kernel
          (flow, cycles, compensation, geometry)
                |
                v
           ExecutionResult
                |
                +--> GUI rendering / playback
                +--> statistics
                +--> batch / CLI trace
                `--> NC / DXF export
```

`ExecutionResult` содержит рассчитанную траекторию, диагностику, шаги выполнения, сигналы, структурные события, состояние WCS и признак полноты выполнения.

### Является ли график OpenGL моделью ЧПУ?

Нет. Отображение использует рассчитанную ядром траекторию. Модуль отображения не интерпретирует G-код самостоятельно.

Это разделение намеренно: одна и та же рассчитанная геометрия используется воспроизведением, статистикой, экспортом и анализом.

### Является ли программа симулятором станка?

Нет. Easy G-Code Plot моделирует поддерживаемую семантику программ FANUC и фрезерных программ SINUMERIK 840D, включая поддерживаемое native-подмножество CAM 3+2/5ax, и геометрию траектории инструмента. Он не моделирует полный физический станок с ЧПУ, динамику сервоприводов, ускорение, инерцию шпинделя, приспособления, рабочие зоны станка или все параметры контроллера.

Чистый результат означает, что смоделированная программа была выполнена без известной ошибки в рамках поддерживаемого контракта. Это не замена проверке на станке.

### Можно ли визуализировать пятиосевые CAM-программы SINUMERIK?

Да, в пределах поддерживаемого native-подмножества фрезерования. `CYCLE800` рассчитывает поддерживаемые статические рабочие плоскости и индексирование 3+2, а `TRAORI` / `TRAFOOF` — непрерывное TCP-движение на профилях `5ax_table_ac_angled` и `5ax_table_bc_angled`. Настроенные поворотные оси, XYZ-геометрия и рассчитанные ориентации инструмента поступают в общий результат для GUI, CLI и остальных потребителей траектории.

Выберите режим фрезерования, откройте native-программу как `.mpf` / `.spf` и укажите соответствующий поворотный профиль. Для предоставленных CAM-примеров `5ax_test.mpf` и `impeller.mpf` есть тесты выполнения до конца программы.

При проверке графика учитывайте диагностику: некоторые native-команды принимаются с предупреждением `UNMODELED_SINUMERIK_NATIVE`, но их эффекты не моделируются. Поэтому достижение `M30` само по себе не подтверждает проверенную геометрию. Точные ограничения циклов, плоскостей и TCP описаны в разделе [SINUMERIK 840D](#sinumerik-840d). У EXPANDED свои ограничения: реконструкция наклонных плоскостей/CYCLE800 при экспорте пока недоступна даже для программ, которые можно визуализировать.

### Что означает детерминированность в этом проекте?

Для поддерживаемого ввода одна и та же программа с одинаковыми настройками даёт одинаковую рассчитанную траекторию и диагностику. Ядро не угадывает поведение контроллера, если необходимые правила неизвестны.

Если траекторию нельзя достоверно рассчитать, ядро выдаёт явную диагностику или неполный результат вместо выдуманной геометрии.

## Начало работы

### Как установить?

Релизные сборки предоставляют отдельные исполняемые файлы GUI и CLI для Windows и архив Linux x64, содержащий оба исполняемых файла. Для упакованных сборок установка Python не требуется.

Для исходного репозитория проект требует Python 3.13+, `uv` и компилятор для нативных расширений.

```bash
git clone https://github.com/MaestroFusion360/easy_gcode_plot.git
cd easy_gcode_plot
uv sync --no-dev
uv run --no-dev python main.py
```

### Каков обычный рабочий процесс в GUI?

1. Откройте или перетащите программу ЧПУ в приложение.
2. Выберите **Lathe Mode** для точения или оставьте отключённым для фрезерования.
3. Настройте WCS, домашнюю позицию и инструменты, когда это требуется программе.
4. Обновите результат выполнения.
5. Проверьте траекторию, воспроизведение, диагностику и статистику.
6. При необходимости экспортируйте FULL, EXPANDED или DXF.

### Какие кодировки ввода поддерживаются?

Обычные кодировки документов — UTF-8 и Windows-1251. GUI показывает файлы `.ptp` в стандартном диалоге открытия и пробует Windows-1251, если чтение как UTF-8 не удалось; при сохранении сохраняется определённая кодировка. CLI предоставляет поддерживаемые кодировки через `--encoding`.

### Принимаются ли компактные блоки FANUC?

Да. Слова не нуждаются в пробелах. Блоки, такие как:

```text
G18G21G40G54G80G99
G0X100Z5
```

разбираются как адресные слова, а не полагаются на разделение по пробелам.

### Какие формы комментариев понимаются?

Распознаются обе распространённые формы:

```text
(КОММЕНТАРИЙ)
; КОММЕНТАРИЙ
```

Постоянный параметр стиля комментариев управляет генерируемым текстовым экспортом. Чтение исходных программ не ограничено выбранным стилем вывода.

### Как работают необязательные строки с пропуском блока `/`?

Исходный блок, начинающийся с `/`, помечается как необязательный.

При включённом **Ignore Block Skip** полный блок исключается из выполнения, включая:

- движение;
- присваивания Macro B;
- сигналы;
- вызовы подпрограмм или макросов.

При отключённом параметре он выполняется нормально.

## Диагностика и поведение при отказе

### Что такое `ok` и `complete`?

`ExecutionResult.ok` показывает, завершилось ли выполнение без критической ошибки. `ExecutionResult.complete` показывает, считает ли ядро результат выполнения достаточно полным, в том числе для экспорта.

Таким образом, программа может сохранить достоверные движения до неподдерживаемого или недопустимого блока, но всё ещё быть помеченной как неполная.

### Какая диагностическая информация хранится?

Диагностика может содержать:

- стабильный код, такой как `UNSUPPORTED_G_CODE` или `UNDEFINED_MACRO`;
- читаемое человеком сообщение;
- серьёзность;
- статус, такой как verified, unverified, unsupported, malformed или resource-limited;
- строку исходного кода;
- offending raw block.

### Что происходит после неподдерживаемой семантики, изменяющей позицию?

Ядро не считает прежнюю позицию достоверной после неподдерживаемой команды, которая может её изменить. При точении построение траектории возобновляется только после того, как последующие абсолютные координаты снова зададут известную позицию.

Это предотвращает рисование вводящей в заблуждение соединительной линии через неизвестную область.

### Как классифицируются неподдерживаемые G-коды точения?

Неподдерживаемый G-код, который может влиять на геометрию, рассматривается более серьёзно, чем негеометрический управляющий код. Например, неподдерживаемый код в блоке, содержащем X/Z/U/W, может сделать блок неподдерживаемым, а не просто непроверенным.

Движение по оси Y не моделируется в `fanuc_turn` и выдаёт `UNSUPPORTED_AXIS`.

### А что насчёт неподдерживаемых M-кодов?

Ядро отслеживает смоделированные сигналы управления программой и станком. Режим batch/analyze дополнительно выдаёт предупреждения `UNSUPPORTED_M_CODE` для явно указанных токарных M-кодов, действие которых на станок не моделируется.

### Обнаруживаются ли конфликтующие модальные коды?

Да. Поддерживаемые модальные группы проверяются на конфликты в одном блоке. Конфликт, такой как два взаимоисключающих режима движения, плоскости, единиц, компенсации, подачи, шпинделя или преобразования, выдаёт `MODAL_GROUP_CONFLICT`, и блок не интерпретируется молча с использованием удачи порядка исходного кода.

### Существуют ли ограничения ресурсов выполнения?

Да. Бюджет выполнения по умолчанию защищает от неуправляемых макросов, рекурсивных вызовов и патологических циклов:

| Ресурс | По умолчанию в GUI |
| --- | ---: |
| Выполненные блоки | 500 000 |
| Вызовы подпрограмм/макросов | 10 000 |
| Сгенерированные движения | 2 147 483 647 |
| Максимум сегментов автообновления | 2 147 483 647 |
| Итерации цикла | 100 000 |
| Итерации макро-цикла | 100 000 |
| Общая глубина вызовов | 64 |

Отмена проверяется через тот же механизм бюджета. Исчерпание ресурсов даёт структурированный результат типа `RESOURCE_LIMIT` вместо неограниченного выполнения.

## FANUC Macro B и поток программы

### Насколько полна поддержка Macro B?

Macro B является частью среды выполнения, а не препроцессором текстовой подстановки. Выражения вычисляются во время выполнения программы, поэтому циклы, ветвления, вызовы подпрограмм и состояние переменных влияют на рассчитанную траекторию.

Одна и та же среда выполнения Macro B используется для точения и фрезерования.

### Какие формы переменных поддерживаются?

Числовые переменные:

```text
#1
#100
#500
#13001
```

Именованные переменные:

```text
#<NAME>
#<TOOL_RADIUS>
```

Косвенные ссылки:

```text
#[#1]
#[100+#2]
#[FUP[#[ROUND[#3]]]]
```

Косвенное присваивание также поддерживается:

```text
#1=100
#[#1]=5
#[#1+1]=#100+2
```

Косвенное назначение должно разрешаться в целочисленный номер переменной.

### Что особенного в `#0`?

`#0` постоянно пуста.

Ей нельзя присвоить значение:

```text
#0=123
```

выдаёт `INVALID_MACRO_ASSIGNMENT`.

Пустые значения отличаются от числового нуля для проверок равенства:

```text
IF[#1 EQ #0] GOTO10
```

— обычный способ обнаружить пропущенный/пустой локальный аргумент.

В арифметике пустое значение ведёт себя как числовой ноль. Присваивание пустого значения очищает целевую переменную:

```text
#100=#0
```

После этого присваивания `#100` является пустой, а не сохранённой как числовой `0`.

### Что происходит, когда неопределённая переменная используется численно?

Обычная числовая ссылка на неопределённую переменную отказывает с `UNDEFINED_MACRO`.

Специальное поведение сравнения с учётом null используется там, где требуется семантика пустых значений FANUC, например, при сравнениях с `#0`.

### Какие арифметические и реляционные операторы поддерживаются?

Вычислитель выражений поддерживает обычную арифметику и реляционные/логические токены в стиле FANUC, используемые в фикстурах проекта, включая:

```text
+  -  *  /
MOD
EQ  NE  GT  GE  LT  LE
AND  OR  XOR
```

Скобки могут быть вложенными:

```text
X[#100+5]
#10=[[#1+#2]*#3]
```

Компактные выражения, такие как `#1LT#3`, принимаются. AND/OR/XOR приводят операнды к целым и выполняют побитовые операции; Python truthiness не используется. Сравнения возвращают числовые 0/1.

Вычислитель отклоняет степень (`**`), строки, bytes, контейнеры и boolean constants. Пределы: 4096 символов, 512 узлов AST и глубина 64. Числовые константы вычисляются как конечные float. LN требует положительный аргумент; переполнение EXP выдаёт диагностику. BIN/BCD/ADP остаются явно неподдерживаемыми: их controller-specific семантика не подтверждена локальными материалами.

### Какие функции Macro B реализованы?

Текущий вычислитель включает:

```text
ABS
SQRT
SIN
COS
TAN
ATAN
FIX
FUP
ROUND
MIN
MAX
LN
EXP
```

Тригонометрические аргументы и результаты следуют семантике градусов в стиле FANUC.

Поддерживается синтаксис двухаргументного арктангенса FANUC:

```text
ATAN[y]/[x]
```

Например:

```text
#119=ATAN[0.75]/[1.625]
```

`ROUND` использует округление до ближайшего целого в стиле FANUC с `.5` от нуля.

### Поддерживаются ли присваивания в блоках с метками?

Да. Метка блока `N` может предшествовать оператору потока Macro B или присваиванию:

```text
N900 #151=7
```

Метки индексируются один раз для выполнения потока.

### Поддерживается ли безусловный `GOTO`?

Да:

```text
GOTO100
...
N100 ...
```

Отсутствующая цель выдаёт `FLOW_TARGET_MISSING`.

### Поддерживается ли `IF [...] GOTO`?

Да:

```text
IF[#1 EQ 2] GOTO900
IF[[#2*#11] GT 360] GOTO16
```

Условия вычисляются во время выполнения с использованием текущего состояния переменных.

### Поддерживаются ли циклы `WHILE / DO / END`?

Да:

```text
#1=0
WHILE[#1 LT 3] DO1
#1=#1+1
G1 X#1 F100
END1
```

Идентификаторы вложенных циклов индексируются перед выполнением. Отсутствующий `END`, несогласованный `END`, неуправляемые циклы или исчерпанный бюджет итераций макроса дают диагностику вместо зависания приложения.

### Тестируются ли реальные фрезерные программы Macro B?

Да. Регрессионный корпус включает программы Macro B, которые генерируют:

- повторяющееся фрезерование бобышек;
- фрезерование плоскости;
- фрезерование отверстий;
- резьбофрезерование;
- вложенные циклы;
- большое количество детерминированных дуг;
- косвенный доступ к переменным.

Они выполняются через обычное ядро фрезерования, а не через отдельный тестовый интерпретатор.

### Поддерживается ли `G65`?

Да. `G65 P...` вызывает макропрограмму `O` и создаёт правильную локальную область макроса.

Пример:

```text
G65 P7700 X0 Y0 M48 S5. D1 R50. Z-70. Q4. V8. I860. A7.5 B15. H24. K1. E100. F200.
```

Вызванный макрос затем может использовать отображённые локальные переменные `#1..#33`.

### Как отображаются аргументы G65 Type I?

Текущее отображение Type I:

| Адрес | Локальная переменная |
| --- | ---: |
| A | #1 |
| B | #2 |
| C | #3 |
| I | #4 при первом появлении |
| J | #5 при первом появлении |
| K | #6 при первом появлении |
| D | #7 |
| E | #8 |
| F | #9 |
| H | #11 |
| M | #13 |
| Q | #17 |
| R | #18 |
| S | #19 |
| T | #20 |
| U | #21 |
| V | #22 |
| W | #23 |
| X | #24 |
| Y | #25 |
| Z | #26 |

`G`, `L`, `N`, `O` и `P` являются управляющими словами и не связываются как обычные локальные аргументы.

### Как обрабатываются повторяющиеся аргументы I/J/K G65?

Повторяющиеся слова I/J/K используют последовательные локальные слоты в стиле FANUC Type II. Каждое появление сдвигается на три:

```text
I -> #4,  #7,  #10, ...
J -> #5,  #8,  #11, ...
K -> #6,  #9,  #12, ...
```

Принимается до 10 появлений каждого адреса I/J/K в одном вызове G65.

### Выполняют ли слова-аргументы G65 также машинные действия?

Нет. В вызове G65 слова, такие как `M`, `S`, `T`, `X`, `Y`, `Z` и `F`, являются аргументами макроса, а не одновременными командами шпинделя, инструмента, движения или подачи.

Например, `T7` или `M8` внутри списка аргументов G65 не создают сигнал смены инструмента или СОЖ.

### Что происходит с `#1..#33` при возврате из макроса G65?

Локальные переменные имеют область видимости.

При входе в макрос локальные переменные вызывающей стороны сохраняются и заменяются аргументами вызова. При `M99` локальные значения вызывающей стороны восстанавливаются. Общие и именованные переменные остаются общими.

Инспектор Macro Variables отражает активную локальную область, пока воспроизведение находится внутри макроса, и показывает восстановленные значения вызывающей стороны после возврата.

### Что делает `G65 ... L...`?

`L` повторяет вызов макроса. Принимаемый диапазон — `1..9999`.

Каждое повторение начинается снова с исходными локальными аргументами G65. Изменения, сделанные предыдущим повторением в `#1..#33`, не просачиваются в следующее повторение.

### Насколько глубоко могут вкладываться макросы G65?

Текущая реализация допускает четыре вложенных уровня локальных переменных G65. Запрос более глубокого вложения макросов выдаёт `CALL_DEPTH_EXCEEDED` вместо молчаливого совместного использования повреждённой локальной области.

Более широкий бюджет стека вызовов M98/G65 отдельно ограничен общей настройкой глубины вызовов.

### Как ведёт себя M98 внутри макроса G65?

Вызов подпрограммы M98 внутри макроса G65 разделяет текущий локальный уровень макроса. Он сам по себе не создаёт ещё одну локальную область G65.

### Поддерживаются ли подпрограммы M98/M99 вне Macro B?

Да.

Типичная форма:

```text
M98 P2000
M98 P2000 L3
...
O2000
...
M99
```

`P` должен идентифицировать существующий положительный целочисленный номер O-программы. `L` должен быть положительным целым числом. Отсутствующие цели и недопустимые значения дают структурированную диагностику подпрограммы.

### Поддерживается ли `M99 P...`?

Нет. `M99 P` зависит от профиля контроллера и в настоящее время выдаёт `UNSUPPORTED_M99_P`, а не угадывает семантику перехода.

### Хранятся ли значения переменных Macro B для каждого шага выполнения?

Да. `ExecutionStep.variables` содержит неизменяемый снимок состояния переменных для этого появления исходного блока. Неизменённые снимки внутренне повторно используются, а не копируются для каждого движения.

Это то, что позволяет инспектору Macro Variables в GUI следовать логическому воспроизведению без повторного запуска программы ЧПУ.

### Сохраняет ли экспорт Expanded Execution операторы Macro B?

Expanded Execution следует фактическому порядку выполненных вхождений. Поток макроса и вызовы G65 разрешаются в результирующее выполнение, а не экспортируются как вторая невычисленная макропрограмма.

Границы подпрограмм и макросов при необходимости сохраняются как события выполнения или комментарии, а сгенерированные движения берутся из рассчитанной ядром траектории.

## FANUC точение

Интерпретатор поддерживает FANUC Type A (по умолчанию) и Type B. Выберите Type B в **Options → CNC / Execution → Lathe G-code system** либо передайте `--lathe-gcode-system B` команде CLI. В Type B коды G90/G91 управляют абсолютными и инкрементальными X/Z, G33 задаёт резьбу, G77/G78/G79 — простые циклы, а G94/G95 — подачу в минуту и на оборот. Type C, модальные макровызовы G66/G67 и операции индексной плоскости G68.2/G53.1 не входят в поддерживаемый токарный язык.

### Основные отличия Type A и Type B

| Операция | Type A | Type B |
| --- | --- | --- |
| Быстрый ход | G00 | G00 |
| Линейное движение | G01 | G01 |
| Дуга по часовой | G02 | G02 |
| Дуга против часовой | G03 | G03 |
| Выдержка | G04 | G04 |
| Нарезание резьбы | G32 | G33 |
| Система координат / ограничение шпинделя | G50 | G92 |
| Чистовой цикл | G70 | G70 |
| Черновое точение | G71 | G71 |
| Черновая подрезка торца | G72 | G72 |
| Повторение контура | G73 | G73 |
| Сверление торца | G74 | G74 |
| Канавки OD/ID | G75 | G75 |
| Многопроходная резьба | G76 | G76 |
| Простой цикл точения | G90 | G77 |
| Простой резьбовой цикл | G92 | G78 |
| Простой цикл торцевания | G94 | G79 |
| Подача в минуту | G98 | G94 |
| Подача на оборот | G99 | G95 |

Type A использует абсолютные X/Z и инкрементальные U/W. В Type B G90/G91 переключают X/Z между абсолютным и инкрементальным режимами; U/W остаются инкрементальными.

### Что представляет собой модель координат точения?

Точение использует геометрию X/Z. Внутренне физическая геометрия X является радиальной, в то время как программируемый X может следовать программированию по диаметру или радиусу.

Состояние точения по умолчанию — программирование по диаметру.

### Как ведут себя X/U и Z/W?

- `X` и `Z` — слова абсолютной оси, где активный режим требует абсолютного программирования.
- `U` и `W` — инкрементальные слова оси точения.
- Преобразование X/U учитывает режим диаметра и радиуса.

Раскрытие циклов использует те же помощники преобразования, а не обрабатывает значения X цикла иначе, чем обычное движение.

### Как обрабатываются G20 и G21?

Ядро нормализует физическую геометрию до миллиметров внутри.

- `G20` устанавливает масштабирование ввода в дюймах;
- `G21` устанавливает масштабирование ввода в миллиметрах.

Выбранный режим единиц фиксируется для каждого шага выполнения, чтобы воспроизведение, статистика и экспорт могли восстановить выполненный контекст единиц.

### Какие форматы дуг точения поддерживаются?

Точение использует круговую интерполяцию G18 XZ с:

- относительным или абсолютным центром I/K согласно Arc Type либо автоматическому определению;
- программированием радиуса R.

Рассчитанные дуги сохраняют точные геометрические данные: центр, радиус, угол и направление.

Дуги R в профиле сохраняют формат R при черновой обработке G71/G72/G73 и чистовом проходе G70 независимо от выбранной трактовки I/K. Если дуга I/K в профиле P/Q некорректна при выбранном вручную режиме, связанный цикл не публикует частичную траекторию и сообщает исходную строку.

### Почему направление G2/G3 может выглядеть инвертированным на графике XZ?

Физическая ориентация G18 и визуальная ориентация графика X/Z — не одно и то же представление координат. Ядро разрешает физическое направление дуги, а слой построения графика использует правильное соглашение XZ, а не рассматривает его как геометрию XY.

### Поддерживается ли прямое программирование угла A при точении?

Да. В обычных токарных блоках G1 программирование угла A может разрешить отсутствующую конечную точку X или Z, используя предыдущее направление контура и запрограммированный угол.

### Поддерживаются ли фаски C и скругления углов R?

Да. Обычные блоки контура G1 могут включать:

- угловые фаски `C`;
- угловые скругления `R`.

Это отличается от `G2/G3 R`, где R — радиус круговой интерполяции.

### Поддерживаются ли движения резьбы G32 и G33?

Да. G32/G33 представлены как синхронизированные резьбовые движения в рассчитанной траектории. Состояние резьбы сохраняется при экспорте и в Stock Removal, где применимо.

### Какие режимы подачи при точении?

Для точения:

```text
G98 -> подача в минуту
G99 -> подача на оборот
```

Режим подачи точения по умолчанию — на оборот.

Время обработки на оборот известно только тогда, когда также доступна достоверная скорость шпинделя. В противном случае статистика сообщает неизвестное время, а не выдумывает скорость подачи.

### Моделируются ли G96 и G97?

Да.

```text
G96 -> постоянная скорость резания (CSS)
G97 -> режим прямых оборотов
```

В режиме CSS значение S хранится как скорость резания. В дюймовом режиме исходное значение скорости резания преобразуется во внутренние метры в минуту.

### Что делает G50 S при точении?

`G50 S...` отслеживается как ограничение скорости шпинделя, используемое с моделью шпинделя точения. Он не рассматривается как операция отмены масштабирования G50 фрезерования.

### Отслеживаются ли сигналы пуска/останова шпинделя?

Да. M3/M4 отмечают работающий шпиндель, а M5 отмечает его остановку. Машинные сигналы, такие как шпиндель, СОЖ, выдержка и конец программы, также публикуются в `ExecutionResult.signals`.

### Какие функции WCS работают при точении?

Ядро поддерживает:

- `G54-G59`;
- расширенные смещения `G54.1 P1-P99`;
- программирование `G10 L2` для G54-G59;
- программирование `G10 L20` для смещений G54.1.

Изменения G10 во время выполнения возвращаются в результате выполнения и не записывают молча настройки приложения.

### Поддерживается ли G53 при точении?

Да, для немодального движения G0/G1 в машинных координатах.

Токарный `G53 G2/G3` не может быть смоделирован текущим контрактом и выдаёт `UNSUPPORTED_G53_MOTION` вместо выполнения как дуги относительно WCS.

### Как работает G28?

Когда включена настроенная эмуляция возврата в референсную точку, G28 разрешает промежуточную запрограммированную точку, а затем выдаёт настроенное движение в машинный ноль. События возврата в референсную точку также записываются структурно.

### G30 — то же самое, что G28?

Нет. Проект не переиспользует молча настроенный домашний G28 в качестве второй референсной точки для G30. Референсная точка G30, зависящая от контроллера, не должна выдумываться из конфигурации G28.

### Как работает компенсация радиуса при вершине резца?

Состояние G40/G41/G42 отслеживается при точении. Если задан подходящий токарный инструмент с известной геометрией вершины, ядро может рассчитать траекторию с компенсацией.

Геометрия инструмента сама по себе не включает коррекцию. Профили G71/G72/G73 используют коррекцию вершины только при явно активной G41/G42, включая команды внутри контура P-Q. Без G41/G42 изменение настроенного радиуса вершины не меняет программируемую траекторию; припуски U/W цикла продолжают учитываться.

Слой компенсации работает с выполненными движениями и геометрией инструмента, а не переписывает исходный текст.

Если требуемая геометрия не может быть безопасно установлена, результат не представляется как проверенное компенсированное движение.

## Циклы точения

### Какие циклы точения моделируются?

Текущий слой циклов точения включает:

| Type A | Type B | Назначение в ядре |
| --- | --- | --- |
| G70 | G70 | Чистовой контур P-Q |
| G71 | G71 | Продольная обдирка |
| G72 | G72 | Торцевая обдирка |
| G73 | G73 | Обдирка повторением шаблона |
| G74 | G74 | Сверление/прорезка торца с периодическим выводом по Z |
| G75 | G75 | Сверление/прорезка по X с периодическим выводом |
| G76 | G76 | Двухстрочная многопроходная резьба |
| G83 | G83 | Осевое сверление с периодическим выводом |
| G84 | G84 | Осевое нарезание резьбы метчиком |
| G90 | G77 | Модальный цикл продольного точения |
| G92 | G78 | Модальный цикл резьбы |
| G94 | G79 | Модальный цикл торцевой обработки |

Геометрия цикла раскрывается в обычные логические движения. Эти движения затем потребляются воспроизведением, статистикой, Stock Removal и экспортом.

### Помнят ли движения цикла, откуда они пришли?

Да. Сгенерированные движения помечаются как сгенерированные циклом и сохраняют принадлежность к источнику, такую как вызывающий блок, исходный текст и группа воспроизведения, где применимо.

Именно поэтому один исходный блок цикла может владеть многими логическими движениями воспроизведения без потери навигации по редактору.

### Как выбираются профили циклов по P и Q?

Циклы контура P/Q разрешают метки N в разобранной программе. Резолвер обрабатывает повторяющиеся метки относительно места вызова цикла, а не предполагает, что каждая метка N глобально уникальна.

Для чистовой обработки предшествующий профиль P-Q может быть предпочтительнее, где это уместно.

### Поддерживают ли блоки профиля G71/G72/G73 линии и дуги?

Да. Контур P-Q строится как сегменты профиля и может включать поддерживаемую линейную и круговую геометрию. Аналитические данные дуги сохраняются, где возможно, вместо преобразования каждой дуги профиля в ступенчатую форму.

### Как работает G70?

`G70 P... Q...` строит указанный чистовой контур и подходит к нему из фактической позиции вызова G70.

Чистовой путь основан на номинальном профиле P-Q, а не на профиле со смещением обдирки, используемом G71/G72/G73.

Если активна компенсация радиуса при вершине резца и может быть проверена, чистовой контур использует компенсированный профиль.

После группы чистовой обработки цикл возвращается в сохранённую позицию вызова, используя детерминированный порядок возврата точения проекта.

### Какая форма G71 поддерживается?

Моделируется обычная двухстрочная форма FANUC:

```text
G71 U... R...
G71 P... Q... U... W... F...
```

Первая строка фиксирует глубину обдирки и отвод. Вторая строка задаёт профиль P-Q, припуски на чистовую обработку и подачу.

### Как интерпретируется глубина G71?

Глубина U первой строки рассматривается как радиальная глубина и последовательно преобразуется в программируемое движение по диаметру, когда активно программирование по диаметру.

Пустой профиль P-Q или нулевая глубина первой строки выдаёт явную диагностику G71; частичная траектория цикла не публикуется.

### Как обрабатываются припуски на чистовую обработку G71 U/W?

U и W второй строки применяются к профилю обдирки до генерации черновых проходов.

U имеет знак. Это важно для наружной и внутренней обработки:

- положительный U оставляет наружный материал на наружном контуре;
- отрицательный U может оставить материал в сторону внутренней поверхности отверстия на внутреннем контуре.

Знак не отбрасывается путём безусловного взятия абсолютного значения.

### Как G71 различает обдирку по наружному и внутреннему диаметру?

Цикл сравнивает подход со стороны заготовки и геометрию профиля и выбирает поведение расточки или наружной обработки. Используется тот же движок контура P-Q, но направление прохода и направление отвода следуют выбранной стороне материала.

### Что такое поведение G71 Type I?

Type I рассматривается как монотонная продольная обдирка. Каждый черновой проход параллелен Z и заканчивается на профиле обдирки P-Q.

После черновых проходов реализация добавляет один полный проход по уже смещённому на припуск профилю обдирки. Она не переиспользует неправильно номинальный чистовой контур на этом этапе.

### Поддерживается ли G71 Type II?

Профиль Type II обнаруживается, когда первый блок P содержит как компонент X/U, так и компонент Z/W.

Реализация может следовать немонотонной/карманной геометрии профиля, используя обрезанные сегменты профиля. Зависящие от контроллера случаи обрабатываются консервативно; неподдерживаемая геометрия не упрощается молча.

### Как работает G72?

G72 использует ту же инфраструктуру профиля P-Q, что и G71, но выполняет торцевую обдирку в плоскостях Z.

Типичная двухстрочная форма:

```text
G72 W... R...
G72 P... Q... U... W... F...
```

Первая строка фиксирует осевую глубину и отвод. Вторая строка ссылается на профиль и припуски на чистовую обработку.

### Является ли G72 Type II полностью универсальным?

Нет. Type II поддерживается там, где плоскость торцевой обработки разрешается в детерминированный диапазон профиля. Если одна плоскость торцевой обработки создаёт несколько несвязных диапазонов материала, требующих зависящей от контроллера интерпретации, выполнение явно отказывает с:

```text
UNSUPPORTED_G72_TYPE_II_SPANS
```

вместо выбора произвольного диапазона.

Пустой профиль, нулевая глубина прохода или одиночное внутреннее пересечение после замкнутого диапазона Type II также выдают явную диагностику. Необрабатываемый диапазон торцевой обработки Type II сообщается как ошибка, а не как пустое расширение.

Повторные пересечения в одной и той же конечной точке замкнутого контура считаются одним пересечением. Различные несвязные диапазоны по-прежнему выдают `UNSUPPORTED_G72_TYPE_II_SPANS`.

### Как работает G73?

G73 реализован как повторяющиеся смещённые копии профиля обдирки.

Первая строка фиксирует общее смещение шаблона U/W и количество проходов R. Вторая строка задаёт P/Q, припуски на чистовую обработку и подачу.

Знаки запрограммированных U/W сохраняются. Цикл не выводит направление смещения из того, как инструмент случайно подошёл к контуру.

### Как работает G74?

G74 поддерживает поведение периодического вывода по Z и повторение в стиле прорезки торца.

Первый блок, содержащий только R, может установить расстояние отвода. Исполняющий блок может использовать X/U и Z/W плюс параметры P/Q/R/F.

Если целевое значение X не задано, G74 может работать как сверление по Z в стиле периодического вывода на текущем X.

Когда запрашивается повторение по X, P управляет шагом X, а Q управляет глубиной периодического вывода по Z. Цикл возвращается к сохранённому началу, используя явный порядок возврата сначала по Z.

### Как работает G75?

G75 выполняет периодический вывод/радиальную прорезку по X.

P управляет радиальным шагом периодического вывода. Q может повторять канавки вдоль Z. Если Q опущен, запрограммированный Z/W выбирает одно место канавки, а не рассматривается как недопустимое повторение с нулевым шагом.

Значение R из установочного блока управляет расстоянием отвода, а значение R исполняющего блока обрабатывается как припуск по дну, где применимо.

### Как представлено движение сверления с периодическим выводом при точении?

Ядро выдаёт фактические примитивы подачи и ускоренного хода для каждой последовательности периодического вывода/отвода. Оно не хранит G74/G75 как непрозрачный цикл, который рендерер должен понимать отдельно.

### Как работает двухстрочный G76?

Моделируемая форма — двухстрочный G76 в стиле FANUC:

```text
G76 P...... Q... R...
G76 X... Z... P... Q... R... F...
```

Первый блок хранит:

- упакованные управляющие цифры P;
- минимальное радиальное приращение Q;
- необязательный припуск на чистовую обработку R.

Второй блок задаёт:

- конечный X резьбы;
- конечный Z;
- высоту резьбы P;
- первый рез Q;
- необязательную конусность R;
- шаг F.

### Как интерпретируются целочисленные приращения P/Q в G76?

Q первого блока и P/Q второго блока рассматриваются как целочисленные приращения наименьшего ввода, а не обычные слова с плавающей длиной.

Для метрического точения они преобразуются в тысячные доли миллиметра. Дюймовый режим использует соответствующее приращение 0,0001 дюйма, преобразованное в физические миллиметры.

### Как генерируется глубина проходов G76?

Проходы резьбы используют прогрессию убывающей глубины / приблизительно постоянной площади стружки, основанную на глубине первого реза и квадратичном соотношении проходов, при соблюдении минимального радиального приращения и припуска на чистовую обработку.

Конечное заданное значение X определяет итоговый диаметр резьбы.

### Что означают упакованные цифры P в G76?

Упакованный P первой строки декодируется как:

```text
P(m)(r)(a)
```

где поля представляют:

- количество финальных/пружинных проходов;
- величину фаски в десятых долях шага;
- угол инструмента/резьбы.

### Какие углы инструмента G76 моделируются?

Поддерживаемый набор:

```text
0, 29, 30, 55, 60, 80 градусов
```

Другие упакованные углы явно отказывают с:

```text
UNSUPPORTED_G76_TOOL_ANGLE
```

Для поддерживаемых ненулевых углов начало/конец прохода по Z сдвигаются, чтобы моделировать односторонний ввод по задней грани в стиле FANUC, а не игнорировать цифры угла.

### Как моделируется фаска G76?

Упакованные цифры фаски преобразуются в осевую длину фаски на основе шага резьбы. Конечная часть каждого прохода резьбы разбивается при необходимости для представления секции фаски.

### Является ли G92 модальным циклом резьбы?

Да.

Пример:

```text
G92 X18 Z-10 F1.5
X17.5
X17.0
```

Начальный G92 устанавливает конец резьбы и шаг. Последующие блоки только с X/U продолжают активный цикл G92 с новыми глубинами до отмены другим явным режимом движения/цикла.

Каждый проход раскрывается в примитивы подхода, синхронизированного продольного резания, отвода и возврата.

### Является ли G90 модальным циклом точения?

Да. G90 устанавливает цикл продольного прямоугольного точения. Последующие блоки только с X/U могут продолжать активный цикл на новых диаметрах до отмены другим явным кодом движения/цикла.

### Является ли G94 модальным циклом торцевой обработки?

Да. G94 устанавливает цикл торцевой прямоугольной обработки. Последующие блоки только с Z/W могут продолжать активный цикл на новых положениях торца до отмены.

### Что отменяет G90/G92/G94?

Немодальный код, такой как G96/G97, не отменяет активный цикл.

Другой явный код движения или цикла отменяет старый модальный цикл точения, если только тот же цикл явно не присутствует в блоке.

### Являются ли G83 и G84 при точении модальными?

Да. G83 и G84 остаются активными для последующих подходящих блоков координат до отмены G80, другим состоянием цикла или сменой инструмента.

### Как ведёт себя G83 при точении?

G83 — осевой цикл сверления по Z.

- Если задан Q, генерируются периодические выводы по Z.
- Если Q отсутствует, ядро не выдумывает глубину периодического вывода; оно выдаёт один ход подачи на глубину и ускоренный возврат.
- Необязательное позиционирование по X обрабатывается перед осевым ходом и восстанавливается после.

### Как ведёт себя G84 при точении?

G84 — осевой цикл нарезания резьбы метчиком. Ход вниз и возврат являются синхронизированными движениями подачи; возврат не представлен как ускоренное перемещение.

### Создаёт ли выдержка P в G83/G84 при точении геометрию?

Нет. Выдержка — это событие времени/управления, а не пространственный сегмент. Поэтому геометрия обратного построения не выдумывает движение для самой выдержки.

### Что произойдёт, если модальный цикл сверления/нарезания резьбы останется в недопустимом состоянии?

Среда выполнения может сообщить об ошибке выполнения класса `UNCLOSED_CYCLE`, а не молча нести невозможный модальный цикл до конца программы.

### Какие M-функции фрезерования распознаются?

| M-код | Функция в ядре |
| --- | --- |
| M00 / M01 | Сигнал остановки / необязательной остановки |
| M02 / M30 | Завершение программы |
| M03 / M04 / M05 | Сигналы вращения шпинделя по / против часовой стрелки / остановки |
| M06 | Событие смены выбранного инструмента T |
| M07 | Распознаётся; действие для конкретной системы охлаждения не моделируется |
| M08 / M09 | Сигналы включения / выключения охлаждения |
| M19 | Сигнал ориентации шпинделя; S в этом блоке задаёт угол, а не обороты |
| M29 | Подготовка жёсткого резьбонарезания; S в этом блоке задаёт обороты для следующего G84 |
| M98 / M99 | Вызов подпрограммы / возврат из неё |

Неизвестные M-коды дают предупреждение `UNSUPPORTED_M_CODE`. Распознаваемые M-коды описывают сигналы и поток программы, но не моделируют оборудование станка.

`M29 S500` перед `G84` помечает жёсткое резьбонарезание в результате выполнения. При `G95` значение `F1.5` означает 1,5 мм/об в метрическом режиме; при `G94` эквивалентная подача для 500 об/мин — `F750` мм/мин. `G80` сбрасывает подготовку к жёсткому резьбонарезанию. Синтаксис M29 и необходимость его применения зависят от конфигурации станка. Ядро фиксирует семантику синхронизации, но не моделирует энкодер или разгон шпинделя.

### Какое базовое движение фрезерования моделируется?

Ядро фрезерования поддерживает ускоренное, линейное и круговое/винтовое движение XYZ в активной плоскости G17/G18/G19.

Объект `TraceMotion` содержит рассчитанную трёхмерную геометрию, хотя многие команды ЧПУ задают движение в плоскости.

### Как обрабатывается индексированное поворотное фрезерование?

Выберите профиль в **Настройки → Поворотная кинематика** или передайте `--kinematics PROFILE_ID` с `--lang fanuc_mill` в CLI. Выбор GUI сохраняется как `CNC/ROTARY_KINEMATICS`. Профиль сопоставляет программируемые адреса A/B/C со знаковыми поворотными осями. G90 задаёт абсолютный поворотный угол; G91 добавляет приращение. Для проверенных профилей стола последующие движения XYZ, рассчитанные дуги и циклы фрезерования преобразуются в фиксированную систему отображения WCS, а воспроизведение ориентирует предварительный просмотр инструмента в рассчитанной точке вершины инструмента. Сами оси WCS не поворачиваются.

Возврат в опорную точку G28 и немодальный G53 сначала используют координаты осей станка, включая повторные возвраты и приращения G91, затем отображают свои точки трассы в индексированную систему отображения. Активная WCS остаётся выбранной после G53. Индекс A/B записывает событие и изменяет последующую геометрию; в настоящее время ядро не генерирует дискретизированную трассу вершины инструмента во время поворотного движения. График опускает соединительную линию через это изменение позиции.

Для проверенного профиля `4ax_table_c` одновременные блоки подачи X/C и блоки только C отображают свои конечные точки в фиксированную плоскость XY. Здесь X — это программируемый радиус, а C — угол вокруг Z; контурную выборку обеспечивает исходная программа. Эти блоки записывают `ROTARY_MOTION`, а не событие индексации.

### Какие поворотные профили были проверены?

Профили `4ax_table_a` и `4ax_table_b` были сопоставлены с программами в `tests/fixtures/milling/indexed_table_a.nc` и `tests/fixtures/milling/indexed_table_b.nc`. Профиль `4ax_table_c` проверяется по `tests/fixtures/milling/indexed_table_c.nc`: его контур X/C накладывается на первый контур XY программы с точностью до 0.05 мм в выборочных конечных точках. Файлы фикстур — это эталонные входные данные, а не определения станка. Автоматические проверки также охватывают знаки углов A/B, G90/G91 и поведение повторных G28/G53.

Каталог также содержит профили головы, смешанные профили голова/стол и другие профили с двумя поворотными осями. Они остаются в JSON с `enabled: false` и скрыты из GUI. Доступны профили `4ax_table_a`, `4ax_table_b`, `4ax_table_c`, `5ax_table_ac_angled` и `5ax_table_bc_angled`; по умолчанию выбрано **Нет**. Наклонные столы AC/BC поддерживают индексированное 3+2 через G68.2/G53.1. Схема не определяет расположение поворотных шарниров, поведение относительно центра инструмента или смещения, зависящие от контроллера.

Редактор JSON проверяет профиль и сохраняет его в `rotary_profiles.json` рядом с `config.ini` пользователя. Он не изменяет установленный каталог. Выбранный профиль явно определяет ось стола/головы и знак; программное обеспечение не может вывести эти свойства из слова A, B или C. Шаги выполнения сохраняют выбранную WCS и настроенные поворотные углы. G10 L2 и изменения WCS сохраняют текущую позицию станка после индексации стола.

Если пользовательский файл профиля повреждён или недействителен, GUI и JSON-editor открывают встроенные профили. Сохранение корректного профиля восстанавливает override и сохраняет исходные повреждённые байты в `rotary_profiles.json.invalid-*.bak`. Другие корректные overrides сохраняются. Загрузки ядра и CLI остаются строгими до исправления файла.

### Что происходит, когда индексированная геометрия не может быть разрешена?

Изменённый адрес A/B/C без выбранного профиля или адрес, отсутствующий в выбранном профиле, останавливает выполнение фрезерования с явным диагностическим сообщением. Одновременное поворотное/XYZ-движение и неповоротная интерполяция с ускоренным ходом также останавливаются для индексированных профилей A/B; исключением является проверенный плоский контур подачи X/C `4ax_table_c`. Это текущая реализация, а не общее ограничение FANUC. A/B/C с неподдерживаемым G-кодом, изменяющим позицию, также останавливает выполнение. Неизвестные M-коды и G41/G42, которые невозможно проверить из-за отсутствующего инструмента или неподдерживаемых данных контура, выдают предупреждения и позволяют выполнению продолжиться. G30 не моделируется как G28: его зависящая от контроллера вторая опорная точка не выводится из настроенного дома G28.

Для `4ax_table_c` компенсация радиуса фрезы G41/G42 не поддерживается. Выполнение продолжается, но график X/C показывает запрограммированную траекторию вершины инструмента без смещения радиуса фрезы и сообщает `UNSUPPORTED_TABLE_C_CUTTER_COMPENSATION`. G40 отменяет модальный запрос. Не рассматривайте этот график как проверенный компенсированный контур.

Выбранный профиль делает расчёт воспроизводимым; сам по себе он не доказывает, что профиль соответствует физическому станку. Проверяйте диагностику и поддерживаемый контракт, прежде чем использовать `ok` или `complete` как решение об экспорте.

### Какие циклы фрезерования моделируются?

Текущий набор включает:

```text
G73
G80
G81
G82
G83
G84
G85
G86
```

Общая среда выполнения цикла возвращает сгенерированную геометрию, модальные обновления, сигналы и конечную позицию как один результат.

### В чём разница между циклами сверления с периодическим выводом G73 и G83 при фрезеровании?

G73 — высокоскоростное сверление с коротким промежуточным отводом. G83 между проходами возвращается на R, затем быстро подходит с зазором d над предыдущей глубиной и продолжает на подаче. Повторный подход ограничен плоскостью R. Параметр ядра `milling_g83_clearance` задаёт d в миллиметрах, в том числе для дюймовых программ; значение должно быть конечным и неотрицательным. Значение по умолчанию 1,0 мм — допущение модели: настройку контроллера нельзя прочитать из программы. Меняются длина движения на подаче и статистика времени G83; токарный G83 и нативный SINUMERIK CYCLE83 сохраняют отдельное поведение.

В фрезерных циклах сверления глубина выше R вызывает `INVALID_DRILLING_DEPTH`. Z, равный R, допустим и не создаёт рабочего хода сверления.

### Как представлена выдержка G82?

G82 включает свою семантику выдержки, но выдержка сама по себе не создаёт пространственной геометрии.

### Как представлен G84 при фрезеровании?

Нарезание резьбы G84 возвращается с глубины как синхронизированное движение подачи, а не как ускоренное перемещение.

### Как представлен G86 при фрезеровании?

Цикл моделирует семантику остановки шпинделя вместе со своим поведением сверления/возврата.

### Что означают G98/G99 при фрезеровании?

Для циклов фрезерования G98/G99 выбирают поведение возврата цикла. Это не значения режима подачи точения G98/G99.

### Какие режимы подачи при фрезеровании?

Для фрезерования:

```text
G94 -> подача в минуту
G95 -> подача на оборот
```

Статистика вычисляет достоверное время обработки только там, где известна необходимая информация о подаче/шпинделе.

### Какие системы рабочих координат поддерживаются?

Ядро поддерживает:

- `G54-G59`;
- `G54.1 P1-P99`;
- `G10 L2` во время выполнения;
- `G10 L20` во время выполнения.

### Как ведёт себя G10 при G91 во фрезеровании?

Для программирования рабочих смещений во время выполнения инкрементальный режим обновляет существующее выбранное смещение, а не молча заменяет его необработанным инкрементальным значением.

### Как работает G52?

`G52 X/Y/Z` устанавливает сдвиг локальной системы координат для последующего движения. Сам управляющий блок G52 не перемещает инструмент.

### Как работают G68 и G69?

G68 включает поворот координат вокруг запрограммированного центра в активной плоскости. G69 отменяет поворот.

В режиме SINUMERIK ISO-M (`G291`) поддерживается только вариант `G68` при активном `G90` и без вектора `I/J/K`. Варианты с углом G91 или с любым 3D-вектором `I/J/K` распознаются, но не поддерживаются. `G69` остаётся доступен.

Активное преобразование применяется к последующим конечным точкам и векторам дуг I/J/K. Включение или отмена преобразования само по себе не создаёт сегмент движения.

`G68.2 X/Y/Z I/J/K` задаёт наклонную рабочую плоскость 3+2 с углами Эйлера Z–X–Z. Выберите профиль кинематики с двумя разными поворотными осями; поддерживаются схемы стол-стол, голова-голова и голова-стол. Следующий отдельный блок `G53.1` рассчитывает углы выбранного профиля для совмещения физической оси инструмента с локальной +Z; недостижимая ориентация останавливает выполнение. `G69` отменяет наклонную плоскость, сохраняя положение индексированных осей. Эта модель работает только в `fanuc_mill`. Явные адреса A/B/C при активной наклонной плоскости и совмещение с G68 не поддерживаются. Опорные перемещения G53 и G28 используют координаты станка. Экспорт Expanded NC для таких программ недоступен; Full Program сохраняет исходный текст.

### Как работает масштабирование G51/G50?

Фрезерный G51 поддерживает:

- равномерное масштабирование с P, где `P1000` означает коэффициент 1.0;
- поосевые коэффициенты через I/J/K.

G50 отменяет масштабирование фрезерования.

Для SINUMERIK ISO-M в `G51` используется моделируемый вес коэффициента 0,001 (`P2000` означает коэффициент 2,0). Другие варианты веса, заданные параметрами станка, не моделируются.

Центр масштабирования интерпретируется как абсолютные координаты даже при G91, а опущенные оси центра используют текущую позицию.

Поосевое масштабирование дуги может превратить окружность в некруговую геометрию. Ядро сообщает об этом неподдерживаемом случае, а не аппроксимирует его как окружность.

### Поддерживается ли G53 во фрезеровании?

Да. G53 — немодальное движение в машинных координатах. Оно не меняет активную WCS. Абсолютный нуль оси, например G53 Z0, означает настроенный дом станка по этой оси. Ненулевые абсолютные и относительные координаты сохраняют свой смысл.

### Поддерживается ли G28 во фрезеровании?

Да. Ядро разрешает опорный путь через настроенную точку дома станка. G91 G28 Z0 возвращает ось Z к настроенному Home Z; промежуточные и конечные точки рассчитываются в координатах станка.

При 4/5-осевой кинематике G28/G53 отображаются в текущей ориентации стола, без сброса ABC. Например, для стола B при Home Z=500 и нулевом смещении WCS возврат при B0 направлен к глобальному Z=500, а при B180 — к Z=-500. Если Z-возврат пересекает центральную плоскость WCS, выполнение останавливается с ошибкой: проверьте Home Z и смещение WCS. Эта проверка не является проверкой столкновений с моделью детали.

После G28/G53 в 4/5-осевой программе следующий подход может начинаться отдельным участком в новой ориентации стола. Соединяющая линия между участками не рисуется. В обычной 3-осевой программе непрерывность сохраняется, включая G28/G53.

### Как программируются дуги фрезерования?

Фрезерование поддерживает:

- относительные смещения центра IJK;
- абсолютные координаты центра IJK;
- программирование радиуса R.

Выбранная исходная интерпретация разрешается в одно аналитическое представление центра/радиуса/развёртки дуги.

### Что делает автоопределение типа дуги?

Если включено автоопределение, ядро проверяет дуги IJK в порядке их появления в программе до окончательного расчёта геометрии.

Для каждой дуги IJK он сравнивает интерпретации относительного и абсолютного центра, используя настроенный допуск дуги. Первый однозначный кандидат фиксирует режим IJK для этого выполнения.

Дуги только с R игнорируются во время обнаружения, потому что они не различают соглашения IJK.

Если все кандидаты неоднозначны, используется выбранный резервный режим. Анализ/пакет CLI в настоящее время используют относительный IJK в качестве резервного.

Выбор типа дуги в GUI вручную переопределяет автоопределение для текущего документа. Настройка автоопределения остаётся включённой для следующего открытого документа. При точении дуга I/K, интерпретированная с неверным режимом центра, сообщает `INVALID_TURNING_ARC_CENTER`; выбор режима радиуса для дуги без слова R сообщает `TURNING_ARC_REQUIRES_R`.

### Может ли одна программа смешивать дуги R с дугами IJK?

Да. Обнаружение типа дуги определяет интерпретацию IJK. Блок только с R остаётся дугой R независимо от этого решения.

### Поддерживаются ли полные окружности?

Да. Аналитические полные окружности представлены непосредственно ядром.

Когда Expanded Execution просят выдать дуги в формате R, полная окружность экспортируется как две точные полуокружности R, потому что один блок R не может однозначно представить полную окружность.

### Поддерживается ли винтовая интерполяция?

Да. Круговая интерполяция может включать движение вдоль оси, нормальной к активной плоскости, где это позволяет поддерживаемый контракт геометрии.

### Что делает полярное программирование G16/G15?

`G16` включает программирование конечных точек в полярных координатах при фрезеровании, а `G15` возвращает к обычному декартову программированию.

Активная плоскость G17/G18/G19 определяет полярную плоскость:

- первая ось в плоскости = радиус;
- вторая ось в плоскости = угол в градусах.

### Как работает полярный G90?

В абсолютном режиме активное рабочее/локальное начало используется как полюс. Запрограммированные полярный радиус и угол являются абсолютными полярными значениями.

### Как работает полярный G91?

При входе в `G91 G16` текущая позиция становится полюсом. Последующие полярные слова G91 инкрементируют модальный радиус или угол, а опущенные компоненты сохраняют своё предыдущее полярное значение.

### Масштабируют ли G20/G21 полярный угол?

Нет. Радиус — это длина, и он следует единицам. Угол остаётся в градусах.

### Поддерживаются ли полярные дуги G2/G3?

Реализованный контракт полярных круговых дуг требует программирования радиуса R. Программирование центра I/J/K при активном полярном режиме G16 отклоняется с явной диагностикой, а не угадывается.

### Поддерживается ли полярная интерполяция G12.1/G13.1?

Нет.

### Как работает компенсация радиуса фрезы?

G40/G41/G42 использует настроенный диаметр фрезерного инструмента и работает с поддерживаемыми контурами линий, дуг и совместимых винтовых линий.

Для индексированного фрезерования со столом A/B смещение рассчитывается в локальной программируемой рабочей плоскости, прежде чем завершённая геометрия преобразуется в фиксированный график WCS. Выполнение продолжается, когда инструмент или контур не удаётся проверить, с сообщением `UNVERIFIED_CUTTER_COMPENSATION`. В 3D-виде перетаскивание левой кнопкой панорамирует, а перетаскивание средней кнопкой вращает вокруг курсора, как в CNCEditor; предустановка 3D/ISO для стола B показывает +Y вертикально вверх, +X вверх-вправо и +Z вниз-вправо, тогда как стол A сохраняет предустановку вертикального фрезерного станка.

Для `4ax_table_c` компенсация G41/G42 не рассчитывается. Траектория сохраняет запрограммированные координаты вершины инструмента X/C и выдаёт `UNSUPPORTED_TABLE_C_CUTTER_COMPENSATION`; G40 отменяет этот режим. Это ограничение относится к текущей реализации стола C.

Движок компенсации разрешает:

- переходы входа;
- геометрию установившегося смещения;
- стыки линия/дуга и дуга/линия;
- углы;
- переходы выхода G40.

Вставленные переходные движения сохраняют принадлежность к шагу выполнения, чтобы навигация по редактору и экспорт оставались согласованными.

### Что означает `UNVERIFIED_CUTTER_COMPENSATION`?

Исходный код запросил G41/G42, но ядро не смогло доказать допустимый компенсированный путь с доступным инструментом/конфигурацией/геометрией.

Система явно помечает это состояние, а не представляет некомпенсированную геометрию как проверенную компенсацию.

### Применяется ли геометрия длины инструмента G43?

Нет. G43/G49 и значения H отслеживаются для выполнения и экспорта, но смещение H пока не применяется к рассчитанной траектории инструмента.

Это ограничение намеренно, и его не следует интерпретировать как смоделированную позицию станка с компенсацией длины инструмента.

### Поддерживается ли непрерывная пятиосевая TCP-обработка G43.4?

Для fanuc_mill на наклонных профилях стола AC и BC поддерживаются непрерывные перемещения G0/G1 одновременно по линейным и поворотным осям. Активация TCP сохраняет текущую физическую точку в траектории. При выключенном TCP индексация сохраняет программные XYZ и меняет отображаемую ориентацию стола. Дуги G2/G3 при TCP допускают одновременный поворот настроенных осей; XYZ задают траекторию центра инструмента, сохраняются ориентации начала/конца. Сочетание TCP с G68.2 не поддерживается. Это разбор траектории, а не полная симуляция станка или столкновений.

## Библиотеки инструментов и обнаружение инструментов

### Где хранятся постоянные инструменты?

Токарные и фрезерные инструменты хранятся в:

```text
%LOCALAPPDATA%\easy-gcode-plot\tools.db
```

Эта база SQLite является основным источником данных для инструментов Saved Library.

### В чём разница между Current Program и Saved Library?

**Current Program** — временное состояние открытой программы ЧПУ. Явно заданные команды `T` можно обнаружить в программе и сопоставить с геометрией инструмента без изменения постоянной библиотеки.

Сначала операция определяет тип инструмента для запасного варианта. Затем совпадающий номер T в соответствующей Saved Library предоставляет фактическую геометрию, включая сохранённые тип и размеры. Если подходящей корректной записи нет, discovery использует размеры из комментариев программы и дефолт по типу операции. Для фрезерования `T02` соответствует `T2`; для точения `T202` соответствует `T0202`, а разные упакованные номера коррекции остаются отдельными. Ручные изменения Current Program сохраняют приоритет при последующих пересчётах.

**Saved Library** является постоянной и фиксируется в `tools.db` только при принятии окна Tool Library.

### Записывает ли открытие программы обнаруженные инструменты в базу данных?

Нет. Обнаружение инструментов является временным.

### Как представлены номера токарных инструментов?

Токарные выборы сохраняют упакованную форму инструмента/смещения, такую как:

```text
T0909
```

Фрезерные выборы используют номер инструмента, например `T03` становится ключом инструмента `T3`.

### Могут ли комментарии описывать геометрию инструмента?

Да. Обнаружение инструментов распознаёт полезные встроенные и близлежащие комментарии, например:

```text
(T3 D=6. CR=0. - FLAT END MILL)
(OD ROUGH R0.8)
(ID ROUGH R0.8)
(GROOVE H4)
(DRILL)
(TAP)
(THREAD)
(BALL)
(FACE MILL)
(CHAMFER)
```

Размеры интерпретируются с использованием единиц, активных при выборе инструмента.

### Что происходит, когда нет явного указания типа?

Контекст операции даёт практическое временное значение по умолчанию, где возможно:

- фрезерование G81-G83 -> сверло;
- фрезерование G84 -> метчик;
- нативные SINUMERIK CYCLE81/CYCLE82/CYCLE83 -> сверло;
- нативный SINUMERIK CYCLE84 -> метчик;
- точение G32/G33/G76/G92 -> резьбовой инструмент;
- иначе стандартная фрезерная или токарная резервная геометрия.

Нативные циклы классифицируются по AST контроллера с учётом модального MCALL, его отмены и смены инструмента. Названия циклов в комментариях или тексте MSG не определяют операцию. Тип операции имеет приоритет над противоречащей подсказкой типа в комментарии; автоматически найденный сохранённый инструмент сохраняет свою геометрию. Предварительное сканирование не исполняет макросы и не выводит физические размеры резца из траектории. В CLI/API снимок библиотеки можно передать через `execute_program(..., library_tools=...)`; исполнение не загружает локальную SQLite-библиотеку неявно.

Общее исполнение GUI/CLI строит Program/AST один раз, по тому же объекту подбирает инструменты до исполнения движений и затем рассчитывает траекторию. Discovery не запускает повторный проход frontend. Сканер Cython/Python по-прежнему извлекает комментарии и явно заданные номера инструментов; он не исполняет операции контроллера самостоятельно.

Найденный сохранённый инструмент или назначенный дефолт не гарантирует подтверждённую компенсацию. `UNVERIFIED` означает неподтверждённую компенсированную траекторию, а не просто неизвестный инструмент. G41/G42 может оставаться неподтверждённым при отсутствии геометрии, неподдерживаемом инструменте или некорректном входе/траектории, в том числе для именованных инструментов SINUMERIK без соответствующей числовой геометрии. Дефолты по типу операции существовали и до автоматического поиска в библиотеке.

### Распознаются ли выражения T с Macro B как явно заданные инструменты?

Нет. При обнаружении инструментов `T#1` и `T[expr]` намеренно не вычисляются. Обнаружение явно заданных инструментов и полное выполнение программы ЧПУ — разные задачи.

### Какие геометрии токарных инструментов хранятся?

Токарная библиотека использует девять канонических типов геометрии:

- Ромб 80;
- Ромб 35;
- Квадрат;
- Круг;
- Треугольник;
- Канавка;
- Резьба;
- Сверло;
- Метчик.

OD, ID и Face — это фильтры UI для доступных ориентаций трассировки, а не разные классы геометрии. Они не выбирают сторону съёма материала и не меняют результат Stock Removal при одинаковой траектории и физической геометрии.

### Какие фрезерные инструменты можно предварительно просмотреть?

Модель фрезерного инструмента включает плоские, радиусные, сферические, конические сферические, торцевые, дисковые и фасковые фрезы, свёрла и метчики.

### Как задаются длины фрезерного инструмента?

Фрезерный редактор сохраняет две длины в миллиметрах:

- `fluteLength` — длина режущей части от кончика; должна быть больше нуля.
- `bodyLength` — длина нережущей части от окончания режущей части до оправки; может быть нулевой.

Длина до оправки равна `fluteLength + bodyLength` и доступна в редакторе только для чтения. Поле совместимости `length` вычисляется из этой суммы; отдельного `shaftLength` нет. Переключатель Inches меняет отображение; SQLite и экспорт JSON/CSV сохраняют миллиметры.

У торцевых и дисковых фрез `fluteLength` задаёт высоту режущей головки; `cuttingHeight` сохраняется только для старых записей. У конических сферических фрез конус заканчивается на `fluteLength`, затем идёт цилиндрическая нережущая часть до оправки. Эту геометрию используют предварительный просмотр библиотеки и отображение при воспроизведении.

В библиотеке режущая часть показана золотистым цветом, нережущая — серым. В 3D режущая часть по умолчанию жёлтая; тело почти белое в тёмной теме и тёмно-серое в светлой, чтобы отличаться от серых STL-моделей. Настройка цвета инструмента меняет только режущую часть. Инструменты без явно заданного разделения длин отображаются одним цветом.

Старые инструменты с одной `length` сохраняют общую длину и прежний вид без выдуманного разделения. Редактор отмечает такие записи как старые. Изменение прочих полей сохраняет неразделённую запись; ввод длин режущей и нережущей частей задаёт новую модель. Чтение библиотеки не переписывает базу данных.

Обе длины можно указать в комментарии, например `(FLAT END MILL D10 FL25 BL15)`. Размеры комментария учитывают единицы при выборе инструмента. Комментарий только с `L`/`LENGTH` сохраняет общую длину без разделения. При автоматическом обнаружении без указанных длин используются редактируемые значения по умолчанию, а не измеренные размеры.

### Загружает ли выполнение CLI сохранённую библиотеку GUI?

Нет. Запуски CLI используют то же временное обнаружение инструментов на основе исходного кода, что и только что открытая программа. Ручные назначения Current Program GUI и Saved Library не загружаются молча в выполнение CLI.

Это важно для проверки G41/G42: выведенные размеры инструмента нужно проверить, прежде чем полагаться на рассчитанную CLI траекторию с компенсацией.

## Интерфейс, редактор и воспроизведение

### Какие две основные панели GUI?

Левая сторона — редактор QScintilla с подсветкой синтаксиса, номерами строк, поиском/заменой и функциями очистки. Правая сторона — представление траектории OpenGL с осями, сеткой, управлением камерой, выбором траектории и воспроизведением.

Фрезерный 3D-вид использует ортографическую CAD-проекцию. При вращении из видов сверху, спереди и слева параллельные линии остаются параллельными, а видимый размер не зависит от глубины.

### Как импортированный STL влияет на видимость траектории?

В режиме сплошного тела поверхность STL скрывает сегменты траектории за ней. Каркас рёбер не имеет сплошной поверхности, чтобы заслонить эти сегменты. Это меняет только видимость на графике, а не рассчитанную геометрию траектории. Управляйте моделями через **Настройки → Объекты STL**; преобразования, сечения, выбор точек и измерения описаны в следующем разделе.

### Как работать с панелью «Объекты STL»?

Панель **Настройки → Объекты STL** изменяет импортированные объекты сцены STL, не меняя программу G-code. Импортируйте модель командой **Файл → Импорт STL**. В списке панели отображаются загруженные модели; выберите строку, чтобы применить к ней операцию. В списке операций доступны **Базовая точка**, **Положение**, **Преобразование**, **Круговой массив**, **Прямоугольный массив** и **Сечение**. Четыре компактные кнопки сверху управляют отменой, повтором, статистикой и удалением объектов STL.

#### Как импортировать и выбирать модели STL?

Используйте **Файл → Импорт STL**, чтобы загрузить ASCII- или бинарную сетку. Команда **Файл → Недавние STL** повторно открывает недавно использованную модель. Каждый импорт добавляется отдельной строкой в панели; выбранная строка становится целью операций и источником статистики. **Удалить** убирает только выбранную модель. **Файл → Очистить STL** удаляет все модели STL. Эти команды меняют объекты сцены, но не текст редактора и не траекторию G-code.

#### Что делают «Отменить», «Повторить», «Статистика» и «Удалить»?

История **Отменить** и **Повторить** для STL независима от истории текста редактора. Она сохраняет такие действия сцены, как добавление модели, смена базовой точки, перемещение, вращение, отражение, масштабирование, создание массивов, применение или очистка сечения и удаление объекта. Первая импортированная модель задаёт исходное состояние, поэтому отмена не закрывает панель и не удаляет эту первую модель. **Статистика** открывает копируемые измерения выбранного объекта. **Удалить** убирает только выбранную строку; для очистки всей STL-сцены используйте **Файл → Очистить STL**.

#### Как работают базовая точка STL и выбор углов параллелепипеда?

Список **Базовая точка** задаёт точку, вокруг которой выполняются вращение, отражение и масштабирование:

- **Центр** помещает её в центр ограничивающего параллелепипеда исходной сетки.
- **Угол габаритов** задаёт минимальные X, Y и Z исходной сетки и показывает габаритный параллелепипед преобразованного объекта цветом базовой точки.
- **Начало координат** задаёт точку `(0, 0, 0)` координат модели.
- **Пользовательская** включает поля X/Y/Z; введите координаты модели и нажмите **Задать базовую точку**.

У отображаемого параллелепипеда есть восемь угловых точек для выбора. Удерживайте **Shift** и щёлкните левой кнопкой мыши по углу в 3D-графике, чтобы переместить туда базовую точку. Выбранная точка становится крупнее и подсвечивается голубым; остальные семь остаются цветом базовой точки. После выбора режим становится пользовательским, а параллелепипед остаётся видимым, чтобы можно было выбрать другой угол. Выбор Центра или Начала координат выключает режим выбора углов.

На странице **Положение** отображается положение базовой точки в мировых координатах. Введите целевые X/Y/Z и нажмите **Переместить сюда**, чтобы поместить её в эти координаты. Перемещение меняет матрицу объекта, сохраняя форму модели.

#### Как задавать положение и преобразовывать модель STL?

На странице **Преобразование** выберите ось и угол вращения вокруг текущей базовой точки. **Отражение** зеркально отражает объект относительно плоскости, нормаль которой направлена вдоль выбранной оси X, Y или Z и проходит через базовую точку. **Масштабирование** применяет одинаковый коэффициент по всем осям относительно этой точки. Исходная STL-сетка сохраняется, меняется только преобразование объекта в сцене; файл на диске не перезаписывается.

#### Как работают массивы STL?

**Круговой массив** создаёт заданное число копий вокруг выбранной оси и центра на указанном общем угле. Нажмите **Создать**, чтобы построить массив. Если включён флажок **Вращать копии**, каждая копия поворачивается вместе со своим положением. Если флажок выключен, копии сохраняют ориентацию, а базовые точки размещаются по окружности. Для полного оборота 360° копии распределяются равномерно без дублирования первой копии в конце.

**Прямоугольный массив** создаёт копии вдоль X, Y и Z. Задайте количество копий и шаг для каждой оси, затем нажмите **Создать**. Исходный объект входит в массив. Создание массива считается одним действием истории STL и отменяется одной командой.

#### Как выполнить 3D-сечение модели STL?

На странице **Сечение** выберите ось X, Y или Z, координату плоскости и сторону, которую нужно оставить. Изначально координата равна середине ограничивающего параллелепипеда выбранной модели в мировых координатах. Кнопка **Применить** обрезает сплошную модель в 3D и закрывает срез там, где сетка образует замкнутый контур; результат остаётся видим поверх исходной траектории. Кнопка **Очистить** возвращает целую STL-модель. Применение и очистка сечения отменяются через историю STL.

#### Что показывает статистика STL и как включить дюймы?

**Статистика** показывает площадь поверхности, объём, центр масс, мировые координаты границ и длины по каждой оси. Границы записываются явно как `Xmin`, `Xmax` и `Length`, а также аналогично для Y и Z. Флажок **Inches** в левом нижнем углу окна пересчитывает все длины, координаты, площадь и объём, не меняя модель. Без флажка значения отображаются в миллиметрах; с флажком — в дюймах, квадратных и кубических дюймах.

В файле STL не задана система единиц, поэтому эти обозначения управляют только отображением и не определяют реальный масштаб исходной модели. Площадь и габариты доступны и для открытых сеток. Для объёма и центра масс требуется замкнутая сетка с согласованным направлением граней; в остальных случаях они помечаются как неопределённые.

### Как изменить регистр букв или пометить необязательные блоки?

Используйте **Правка → В верхний регистр** (`Ctrl+Shift+U`) или **Правка → В нижний регистр** (`Ctrl+U`), либо соответствующие кнопки панели инструментов, чтобы преобразовать выделенный текст. Без выделения они преобразуют весь документ редактора. Их сочетания клавиш можно изменить в параметрах.

Выберите один или несколько блоков и нажмите **Ctrl+/**, чтобы добавить `/` в начало каждого выделенного непустого блока. Нажмите **Ctrl+Shift+/**, чтобы удалить один ведущий `/` из каждого выделенного блока. Без выделения эти команды ничего не делают. Оба сочетания клавиш фиксированы и не могут быть назначены другой команде. Косая черта — это маркер пропуска необязательного блока FANUC; выполняются ли такие блоки, зависит от настройки пропуска блоков.

### Как распечатать график?

Используйте **Файл → Печать** (`Ctrl+P`) или кнопку «Печать» на панели инструментов «Файл». Приложение печатает чёткие векторные линии в текущей ориентации камеры, вписанные в альбомную страницу. Печать игнорирует ползунок воспроизведения и не скрывает линии за импортированным STL. В **Параметры → График** можно показывать или скрывать ускоренные перемещения, отображать их пунктирными или сплошными и раскрашивать все перемещения по инструменту; печать следует этим настройкам. **FAQ** открывается по `F3`, а **Сетка** по умолчанию переключается по `F4`.

### Какие фиксированные виды доступны?

Top, Front и Left — ортогональные виды. Обычный 3D-вид — перспективный. Начало свободного вращения из фиксированного вида возвращает к перспективе.

### Как воспроизведение связано с ядром?

Воспроизведение следует рассчитанным движениям из текущего `ExecutionResult`. При перемещении ползунка исходный код не разбирается заново.

При обычном воспроизведении траектории поддерживаемые аналитические дуги и винтовые движения с неизменной ориентацией инструмента показываются через промежуточные положения курсора и фрезы. Это относится и к полным окружностям, повторяемым циклом Macro B WHILE. Во время этих кадров ползунок остаётся на одном логическом движении и переходит на следующий шаг один раз; качество отрисовки не меняет его диапазон. Даже на максимальной скорости окружность не сводится к скачкам между двумя противоположными точками. Для токарного снятия материала используется отдельная шкала воспроизведения.

Во время воспроизведения кнопка Play показывает значок Pause. Повторное нажатие ставит воспроизведение на паузу; остановка или завершение возвращает значок Play.

### Что делают Step Backward и Step Forward?

Они перемещаются на одно логическое движение, включая сгенерированные движения из циклов и выполнения, раскрытого Macro B.

### Почему многие движения воспроизведения могут соответствовать одной строке исходного кода?

Один исходный блок может выдать много движений. Примеры включают:

- циклы точения;
- циклы фрезерования;
- циклы Macro B, которые выполняют одну и ту же строку исходного кода повторно;
- геометрию компенсированных переходов.

Воспроизведение отдельно отслеживает каждый случай выполнения блока и его связь с исходной программой.

### Как найти отображённое движение в редакторе?

Используйте Shift+Click рядом с траекторией. Приложение выбирает соответствующий исходный блок и перемещает ползунок к нужному движению.

### Перемещает ли автоматическое обновление курсор редактора?

Обычное обновление выполнения/графика предназначено для обновления результата без использования перемещения курсора редактора как побочного эффекта. Воспроизведение/навигация могут намеренно выбирать местоположения исходного кода.

### Что происходит, когда Auto Update слишком дорого?

Auto Update имеет лимит выборочных сегментов. Большие правки могут оставаться в ожидании до явного Refresh, чтобы набор текста оставался отзывчивым.

Если исходный код изменяется во время выполнения обновления, устаревший расчёт отменяется/игнорируется, и ставится в очередь новое обновление.

### Что останавливает Cancel?

Диалог выполнения показывает ресурсоёмкие этапы обработки: чтение и разбор программы, выполнение, обнаружение инструментов, дискретизацию траектории и обновление графика. Отмена выполняется кооперативно: состояние отмены регулярно проверяется на всех этапах.

### Какие помощники редактирования ЧПУ включены?

GUI содержит:

- Hole Calculator;
- Pocket Calculator;
- Snippets.

Hole и Pocket Calculator только для фрезерования. Snippets доступны в обоих режимах станка.

### Что генерирует Hole Calculator?

Он генерирует блоки координат для круговых или прямоугольных/сеточных patterns отверстий. Он не выдумывает полную окружающую логику безопасности цикла сверления.

### Что генерирует Pocket Calculator?

Он может генерировать круговые или прямоугольные фрагменты фрезерования с настраиваемым перекрытием, глубинами, безопасным/референсным Z, подачей, направлением, стратегией очистки, винтовым входом и чистовым проходом.

Сгенерированный фрагмент — отправная точка, а не сертификация безопасности станка.

### Где хранятся сниппеты?

В Windows сниппеты обычно хранятся в:

```text
%LOCALAPPDATA%\easy-gcode-plot\snippets.db
```

Более старые текстовые сниппеты можно импортировать один раз, при этом исходные файлы сохраняются как резервная копия.

Нечитаемый legacy-файл или файл с некорректным UTF-8 пропускается с предупреждением в журнале; остальные сниппеты импортируются. Пропущенный исходный файл остаётся в резервном каталоге. При повреждённых данных порядка используется сортировка по имени файла.

## Параметры и настройка сцены

### Где прочитать ошибки и предупреждения выполнения?

В статусной строке показан один компактный счётчик диагностики, например **Warnings: 2** или **Errors: 1**. Наведите на него курсор, чтобы прочитать полные сообщения с номерами строк исходного кода; диагностика также доступна в **Tokens**. Одинаковые сообщения для разных строк остаются отдельными записями. **READY**, **UPDATING** и **STALE** обозначают состояние расчёта. Длинные временные уведомления сокращаются многоточием с учётом доступного места; полный текст показывается при наведении на статусную строку. Изменение размера окна не продлевает время показа уведомления.

### Как изменить цвет подсветки текущей строки?

Откройте **Настройки → Параметры → Цвета** (**Settings → Options → Colors**). В группе **Редактор** отдельно задаются цвета текущей строки для светлой и тёмной тем: по умолчанию `#e8e8ff` и `#2a2d2e`. Нажмите кнопку с образцом цвета, чтобы открыть системный выбор цвета, либо введите `#RRGGBB`, затем нажмите **OK**. Оба цвета сохраняются независимо; смена темы или типа файла редактора не сбрасывает выбранные значения. **Отмена** сохраняет прежние настройки, а **Восстановить значения по умолчанию** сбрасывает оба цвета. В отдельной группе **График** находятся цвета траектории, инструмента, фона и STL.

Включение и отключение подсветки остаётся во вкладке **Редактор → Подсвечивать текущую строку** (**Editor → Highlight current line**).

### Как изменить язык интерфейса?

Откройте **Настройки → Параметры → Общие** (**Settings → Options → General**). В поле **Язык** выберите **Английский** или **Русский** и нажмите **OK**. Перезапустите Easy G-Code Plot: смена языка применяется после перезапуска, о чём программа выводит уведомление. Эта настройка меняет язык интерфейса, а не диалект ЧПУ для выполнения управляющей программы.

### Как изменить тему?

Откройте **Настройки → Параметры → Общие**, выберите **Светлая** или **Тёмная** в поле **Тема** и нажмите **OK**. Тема применяется сразу, без перезапуска. Выбранные язык и тема сохраняются в конфигурации приложения.

### Где задать рабочие системы координат и значения возврата домой?

Откройте **Настройки → WCS** (**Settings → WCS**). Это отдельный диалог, а не вкладка «Параметров».

| Настройка | Как использовать |
| --- | --- |
| G54–G59 | Введите смещения X/Y/Z для каждой системы. Активную систему выбирает команда G54–G59 в УП; изменение строки диалога не добавляет эту команду в программу. |
| Home (G28) | Задайте координаты опорной точки возврата и отметьте, настроена ли она. Эти значения используются при расчёте возврата G28. |
| X/Z при точении | Поля X задаются в диаметрах; поля Y отключены. Z задаёт осевую координату. |
| X/Y/Z при фрезеровании | Доступны все три координаты; X задаётся как линейная координата. |
| Дюймы | Переключает отображение и ввод длин между миллиметрами и дюймами. Существующие физические значения пересчитываются, а не принимаются за значения в другой единице. |

Нажмите **OK**, чтобы применить значения и пересчитать программу. **Отмена** оставляет сохранённые значения без изменений. Для расширенных смещений G54.1 в этом диалоге нет полей; они остаются нулевыми, пока их не зададут поддерживаемые команды УП, например G10 L20.

### Как задать размеры токарной заготовки?

В режиме точения откройте **Настройки → Заготовка** (**Settings → Stock**). Перед запуском снятия материала задайте размеры исходной заготовки.

| Поле | Назначение |
| --- | --- |
| Наружный диаметр | Исходный наружный диаметр заготовки. |
| Внутренний диаметр | Диаметр исходного отверстия; для сплошной заготовки задайте ноль. |
| Длина | Осевая длина заготовки. |
| Z переднего торца заготовки (Stock front Z) | Абсолютная координата Z переднего торца. Задний торец расположен в `Z переднего торца − длина`; поле задаёт координату, а не только толщину припуска. |
| Точность | Разрешение модели заготовки. Более высокая точность даёт более подробную модель и увеличивает время расчёта. |
| Дюймы | Отображение и ввод размеров в дюймах вместо миллиметров с сохранением физического размера. |
| Запуск снятия материала при нажатии Play | Включает воспроизведение снятия материала при нажатии Play. |
| Сброс к авто (Reset to Auto) | Возвращает размеры, рассчитанные по траектории резания текущей программы. |

Нажмите **OK**, чтобы применить ручные размеры; **Отмена** отменяет изменения в диалоге. Ручные размеры действуют до **Сброса к авто**, создания новой или открытия другой программы. Для снятия материала нужна рассчитанная полная токарная программа и настроенная геометрия инструмента. Автоматический расчёт размеров и поддерживаемые инструменты описаны в разделе [Удаление материала при точении](#удаление-материала-при-точении).

### Есть ли снятие материала при фрезеровании?

Нет. Сейчас снятие материала реализовано только для токарной обработки. Для фрезерования моделирование снятия материала пока отсутствует.

Для геометрии детали при фрезеровании загрузите модель STL и откройте **Настройки → Объекты STL** (**Settings → STL Objects**). Панель позволяет перемещать, поворачивать и копировать модели, создавать массивы и сечения, просматривать статистику. STL отображается вместе с траекторией как опорная модель; перемещения фрезы не вычитают материал из STL.

## Удаление материала при точении

### Что такое Turning Stock Removal?

Это осесимметричный предварительный просмотр удаления материала на основе рассчитанной траектории точения и настроенной геометрии резца.

Это не симуляция станка.

### Как оценивается автоматический припуск?

Рассчитанная траектория резания G1/G2/G3 позволяет определить минимальный наружный диаметр и длину. Выбросы ускоренного хода G0 игнорируются, режущие движения, сгенерированные циклом, включаются, а экстремумы дуг G18 оцениваются аналитически.

### Можно ли переопределить размеры заготовки вручную?

Да. **Настройки → Заготовка** позволяет задать наружный и внутренний диаметры, длину, абсолютную координату Z переднего торца и точность/разрешение. Поля и включение воспроизведения описаны в разделе [Как задать размеры токарной заготовки?](#как-задать-размеры-токарной-заготовки).

Ручные значения сохраняются до тех пор, пока сброс к авто, создание новой или открытие другой программы не вернёт модель заготовки к размерам, производным от программы.

### Какие инструменты удаляют материал?

Поддерживаемые геометрии токарных инструментов включают девять канонических типов библиотеки инструментов. Stock Removal использует рассчитанную траекторию, ориентацию трассировки и физическую геометрию резца. Флажки OD/ID/Face только фильтруют доступные варианты трассировки в редакторе инструмента; изменение этих фильтров не меняет съём при одинаковой траектории и геометрии резца.

Ограниченный контур перемещения резца удаляет только материал, с которым пересекается. Сохраняются отдельные оставшиеся кольца материала, в том числе наружная стенка при расточке G71. Возврат назад и повторное воспроизведение тех же движений восстанавливают одинаковое сечение заготовки. Для канавок поле **Геометрия канавочного резца** отдельно выбирает радиальную или торцевую геометрию независимо от флажков.

### Как резьбы представлены в Stock Removal?

Синхронизированные режущие движения G32/G33, модального G92 и G76 используют детерминированную модель продольного сечения резьбы, а не развёртывание полного тела пластины как обычного твёрдого тела.

Запрограммированный X определяет глубину впадины, F определяет шаг/ход, а настроенная геометрия резьбы формирует сечение.

Изображение резьбовой пластины — отдельный фиксированный контур, общий для Tool Library и инструмента в Stock Removal: треугольный корпус с тремя маленькими режущими треугольниками 60° и уступами между ними. Активная точка трассировки привязана к запрограммированному положению инструмента. В стандартном токарном виде наружная вершина P8 направлена вниз, внутренняя P6 — вверх.

Контур масштабируется только по диаметру пластины. Исходный контур построен для Ø12; при Ø20 все координаты умножаются на `20 / 12`, примерно 1,667. EX, RC и угол профиля резьбы не деформируют изображение корпуса. Угол остаётся в расчёте съёма, но скрыт в редакторе; в сводке библиотеки показывается ориентация трассировки. Эти изменения отображения не перезаписывают записи инструментов в SQLite.

### Обнаруживает ли Stock Removal столкновения станка?

Нет. Он не моделирует патрон, револьверную головку, приспособления, ускорение или полную геометрию станка.

## Статистика и Tokens/Macro Variables

### Что содержит Toolpath Statistics?

Статистика рассчитывается по траектории и включает:

- количество логических движений;
- разбивку по длине;
- известное и неизвестное время обработки;
- среднюю подачу;
- предполагаемую скорость ускоренного хода;
- границы XYZ;
- секции по инструментам.

Окно Statistics отображает HTML-сводку. Выбор инструмента переключает таблицу между всей программой и одним инструментом. Export HTML сохраняет сводку и все секции инструментов с таким же переключателем и текущими единицами отображения. Только в экспортированном отчёте под таблицей добавляется статичная SVG-проекция: XY для фрезеровки, XZ для токарки. Выбор инструмента фильтрует и изображение. Экспорт из GUI использует ту же подготовленную геометрию, компоновку страницы и стили линий, что Print. Все движения сохраняются. Исходная УП в файл не включается.

Переключатель Inches преобразует значения без изменения физической геометрии. Аналог в CLI: `python -m app analyze program.nc --html statistics.html` (добавьте `--inches` для дюймов).

### Почему время обработки может быть UNKNOWN?

Ядро избегает фабрикации физической скорости подачи. Распространённый случай — движение с подачей на оборот без известной скорости шпинделя.

### Что такое вкладка Tokens?

Tokens отображает разобранные/вычисленные слова, позицию в исходном коде, статус выполнения и диагностику. Подозрительные или неподдерживаемые строки подсвечиваются и могут быть экспортированы в CSV.

### Что такое вкладка Macro Variables?

Macro Variables показывает снимок переменных в текущей позиции логического воспроизведения.

Он следует:

- присваиваниям;
- циклам;
- локальным областям G65;
- выполнению M98 внутри макроса;
- восстановленным локальным переменным вызывающей стороны после M99.

Он использует существующие снимки выполнения и не перезапускает программу ЧПУ при перемещении ползунка воспроизведения.

### Почему Macro Variables могут быть недоступны?

Если результата выполнения не существует, нет истории переменных для показа. Если исходный код редактора изменился с момента отображения результата выполнения, результат устарел, и инспектор переменных ждёт Refresh, а не смешивает новый исходный код со старым состоянием среды выполнения.

## Экспорт

### Какие семейства экспорта GUI существуют?

Для NC/геометрии есть три режима:

- **FULL** — безопасная нормализация исходной УП;
- **EXPANDED** — рассчитанная геометрия/состояния через профиль целевой стойки;
- **DXF** — геометрия траектории.

Tool List и Statistics — отдельные экспорты отчётов, а не режимы NC.

### Повторно ли интерпретируется G-код при экспорте?

Нет. FULL использует точный исходный текст вместе с авторитетной картой исполнения. EXPANDED и DXF используют рассчитанную геометрию/состояния выполнения. Ни один путь не запускает второй интерпретатор ЧПУ.

### Что означает Full Program?

FULL сохраняет обычные исходные кадры, комментарии, модальные команды, диалект и поддерживаемые циклы. Конструкции, зависящие от потока выполнения и меток, раскрываются по карте исполнения до перенумерации: вычисленный Macro B, IF/GOTO/WHILE, вызовы G65 и M98/M99, а также токарные FANUC G70–G76. FULL не конвертирует программу на другую стойку.

### Что означает Expanded Execution?

EXPANDED — путь конвертации между стойками. Один общий постпроцессор выводит рассчитанную геометрию и машинные состояния через JSON-профиль. Циклы, переменные и поток подпрограмм к этому моменту уже исполнены. Профиль цели задаёт синтаксис, обязательные кадры, возможности и значения по умолчанию; он не отключает пользовательские параметры вывода.

Встроенные профили: `fanuc_mill`, `fanuc_mill_multiaxis`, `fanuc_lathe_a`, `fanuc_lathe_b`, `sinumerik_iso`, `sinumerik_840d`, `sinumerik_840d_multiaxis`; внешний JSON выбирается через `--post-profile`. Профили `*_multiaxis` объявляют `supports.axes` `X/Y/Z/A/B/C` и выводят явные resolved rotary coordinates; трёхосевые профили остаются только XYZ и по-прежнему отклоняют rotary-геометрию.

Индексирование вокруг смещённого начала WCS остаётся fail-closed с кодом `UNSUPPORTED_INDEXED_WCS_EXPANDED_EXPORT`: вывод в нулевом G54 не сохраняет центр индексирования без реконструкции смещений целевого frame. Разбиение TCP-дуг распределяет ABC вместе с XYZ; вывод rotary в G91 избегает накопления ошибки округления. Для пользовательского поста с G93 сохраняется длительность исходного кадра, а перед следующим движением восстанавливается исходная подача. Непроверенная компенсация и проигнорированные native-команды, меняющие геометрию, возвращают `UNSUPPORTED_UNVERIFIED_GEOMETRY_EXPANDED_EXPORT` с конкретными кодами диагностики исполнения.

### Что означает Auto (source controller)?

`Auto (source controller)` — не отдельный режим возможностей. Он автоматически выбирает профиль постпроцессора по контроллеру и диалекту источника: токарный FANUC берёт профиль токарки A/B, фрезерный FANUC — `fanuc_mill`, SINUMERIK ISO — `sinumerik_iso`, нативный SINUMERIK — `sinumerik_840d`. EXPANDED всегда пересобирает рассчитанное исполнение, поэтому даже «Auto» — это конвертация; просто не нужно явно указывать цель.

### Как работает Modal Feed?

`Modal Feed` управляет повтором `F`: **Да** выводит `F` только при смене подачи или режима подачи, **Нет** повторяет `F` в каждом режущем перемещении.

### Можно ли выбирать параметры форматирования при конвертации на конкретную стойку?

Да. EXPANDED рассматривает Целевое ЧПУ как целевой синтаксис/профиль, а не как выключатель возможностей. Координаты (G90/G91), номера кадров, разделитель, ведущий ноль, модальная подача, десятичных знаков, десятичная точка и знак плюс, вывод дуг и начало/конец программы остаются доступными и соблюдаются для FANUC → FANUC, FANUC → SINUMERIK ISO, FANUC → SINUMERIK native и SINUMERIK → FANUC. Значение профиля применяется только когда вы его не выбрали. Если профиль объявляет обязательный префикс (например, `G290`/`G291`), он остаётся первым, а ваш текст начала идёт после него. Профиль используется только для реальных ограничений возможностей: rotary/TWP/TCP, отсутствующая ось или неподдерживаемое состояние дуги/подачи.

### Что содержит DXF?

DXF содержит доступную рассчитанную геометрию движений. Быстрые и режущие движения находятся на разных слоях. Для точения используется представление Z/X как на Plot; для фрезерования записываются 3D-линии и аналитические дуги/окружности, где это возможно, а непредставимая одной DXF-дугой геометрия дискретизируется в полилинию.

### Разбирает ли DXF G-код заново?

Нет. DXF writer работает с геометрией движений и не интерпретирует слова стойки или параметры NC-форматирования.

### Какие параметры форматирования NC существуют?

Общие параметры экспорта включают:

- абсолютные/инкрементальные координаты, где поддерживается;
- номера последовательности;
- начало и приращение последовательности;
- интервал номеров последовательности;
- пробелы/без пробелов между словами;
- ведущие нули (`G01` против `G1`);
- комментарии/без комментариев;
- строка безопасности (объявленная в профиле);
- десятичных знаков, десятичная точка и знак плюс;
- начало и конец программы;
- представление дуг фрезерования.

Для EXPANDED этими параметрами управляет пользователь: целевой профиль задаёт синтаксис и значение по умолчанию только для того, что вы не выбрали. Обязательный кадр режима из профиля остаётся первым, а ваш текст начала идёт после него.

### Как пост-профиль управляет порядком и обязательностью вывода слов?

Объект `format.words` в профиле задаёт каждому токену кадра поля `order` и `required`: `motion`, `X`, `Y`, `Z`, `A`, `B`, `C`, `I`, `J`, `K`, `R`. `required=true` выводит адрес при наличии resolved value (например `Y0` вместо пропуска нулевого `Y`); `required=false` допускает обычный пропуск неизменившегося значения. `motion.required=false` делает код движения модальным: `G1` повторяется только при смене движения. `decimals`/`sign` для слова хранятся в том же объекте. Ось допустима только если объявлена в `supports.axes`, а `F` намеренно исключён, поскольку подачей управляет Modal Feed. Обязательность адресов — свойство конкретного post/controller, поэтому она задаётся только в профиле и не имеет отдельной настройки GUI/CLI.

### Какие режимы вывода дуг Expanded для фрезерования существуют?

Контракт CLI предоставляет:

```text
auto
ijk-relative
ijk-absolute
radius
linearized
```

`auto` использует соглашение из пост-профиля. Четыре явных режима: относительные IJK, абсолютные IJK, радиус и линеаризация. Исходный синтаксис дуг уже разрешён до постпроцессинга. Native SINUMERIK выводит абсолютные центры как `I=AC(...)` / `J=AC(...)` / `K=AC(...)`, а радиус — как `CR=`.

### Что происходит, когда полная окружность экспортируется в режиме R?

Она выдаётся как две точные полуокружности R.

### Можно ли преобразовать Expanded NC между миллиметрами и дюймами?

Да. Преобразование единиц выполняется на границе постпроцессора по рассчитанной геометрии/состоянию. Координаты, геометрия дуг, I/J/K или радиус, подачи и поддерживаемые состояния стойки выводятся в выбранных единицах и проверяются повторным исполнением в тестах экспорта.

FULL сохраняет исходник и поэтому принимает только `--units auto`.

### Можно ли принудительно задать Full Program в мм или дюймах?

Нет. Экспорт Full Program CLI в настоящее время принимает только `--units auto`.

Семантическая нормализация единиц — это функция Expanded Execution.

### Какие единицы использует DXF?

DXF может выводиться в миллиметрах или дюймах. `auto` сохраняет текущее поведение DXF по умолчанию, то есть миллиметры.

### Можно ли удалить комментарии из экспорта?

Да. `--no-comments` удаляет исходные комментарии из FULL и подавляет перенос исходных комментариев в EXPANDED. Синтаксис комментариев EXPANDED задаётся выбранным пост-профилем.

### Записываются ли экспорты атомарно службой CLI?

Да. Служба экспорта CLI записывает во временный файл в выходном каталоге, а затем заменяет конечный выходной путь. Неудачная запись не оставляет намеренно частично записанный конечный файл.

### Может ли экспорт CLI перезаписать исходный файл?

Нет. Исходный и выходной пути должны быть разными.

### Можно ли напрямую сравнить экспорт CLI с эталонным NC-файлом?

Да. Добавьте `--compare-with FILE` к экспорту одного NC-файла в режиме FULL или EXPANDED:

```powershell
.\easy_gcode_plot_cli.exe export source.nc --lang fanuc_mill --post-profile sinumerik_840d -o actual.mpf --compare-with expected.mpf
```

CLI сравнивает фактически сгенерированный файл с эталоном в UTF-8. Окончания строк LF и CRLF считаются одинаковыми; пробелы, комментарии и завершающий перевод строки сравниваются. Код завершения `0` означает совпадение, `1` — расхождение, `2` — ошибку экспорта или работы с файлом. При расхождении в stdout выводится unified diff без временных меток: сначала эталон (`---`), затем результат (`+++`). Сгенерированный файл сохраняется; эталон не может быть выходным файлом и не перезаписывается. Для DXF и `batch-export` этот параметр недоступен.

Это прямая регрессионная проверка текста. Проверки исполнения и повторного исполнения экспорта по-прежнему нужны для семантической эквивалентности, когда разный NC-текст описывает одну операцию.

## SINUMERIK 840D

**Options → General → 840D Extended cycles** выбирает интерфейс циклов для чтения native-программы и её native-экспорта EXPANDED. Включён (по умолчанию): интерфейс Siemens 03/2009, CYCLE81/82/83/84 с 9/9/20/24 параметрами. Выключен: классический интерфейс 01/2008 с 5/6/17/18 параметрами. Короткие совместимые вызовы принимаются; сигнатуры 840D Extended cycles в классическом режиме дают диагностику. Изменение настройки пересчитывает текущую программу. Выбор не меняет G290/G291 и кинематику: совместимость определяется установленным пакетом циклов, а не одним названием платформы. В CLI используется `--sinumerik-cycles classic|sl`; в JSON native-постов оба набора находятся в `cycleProfiles.classic_0108` и `cycleProfiles.sl_0309`.

В корпус также входят [ext_cycles.mpf](tests/fixtures/milling/sinumerik/ext_cycles.mpf) и [no_ext_cycles.mpf](tests/fixtures/milling/sinumerik/no_ext_cycles.mpf), сохранённые как выданы постпроцессором. Это программы аудита с поддерживаемыми и неподдерживаемыми операциями, а не примеры полностью успешного исполнения. Общие CYCLE81/82/83 дают одинаковую геометрию в соответствующих профилях. Расширенный файл впервые останавливается на строке 216: CYCLE84 с дроблением стружки не моделируется. Классический — на строке 200: объявление CYCLE84 содержит 21 позиционный параметр при текущем лимите 18. Левая и глубокая резьба, CYCLE85/86/87/89 и native M19 не моделируются. Выбор расширенного интерфейса не включает эти операции.

Интерпретация центров дуг определяется режимом в момент исполнения: native и ISO-M (`G291`) используют относительные IJK; в native абсолютный центр явно задаётся I=AC/J=AC/K=AC. В смешанной программе `G290/G291` каждая дуга разрешается в своём активном режиме; настройка дуг документа и автоопределение не переопределяют эту семантику. В native доступны настроенные поворотные оси в пределах поддержанного TCP/indexing subset; в G291 поворотные A/B/C отклоняются.

Результат исполнения и структурированные CLI/batch-отчёты содержат `source_dialect` (`fanuc` или `sinumerik`) независимо от общей геометрической модели `fanuc_mill`. Это семейство исходной программы, а не один режим для всей смешанной программы. Конкретные неподдержанные G/M-коды SINUMERIK учитываются в сводке batch; ошибки синтаксиса и функций не превращаются в выдуманные G/M-записи.

Цель поддержки SINUMERIK — **визуализация траекторий с нативными командами и циклами, которые выдаёт постпроцессор CAM**. Сложный внутренний макроязык Siemens не входит в область реализации: его полноценная поддержка силами одного человека не представляется возможной. Исполнение подпрограмм из режима SDI пока также недоступно. SPF можно открыть как документ, но это не означает поддержку произвольных вызовов подпрограмм Siemens.

MPF/SPF сохраняют выбранный поворотный профиль. Меню Settings и список Options остаются доступными. Native CYCLE800/TRAORI поддерживают наклонные столы AC/BC; несовместимые профили, оси и поворотные команды ISO-M отклоняются ядром с диагностикой.

### Какая поддержка SINUMERIK включена?

Приложение поддерживает ограниченное нативное подмножество Siemens (`G290`, также начальный режим MPF/SPF) и ISO Dialect M (`G291`). Оба режима используют общее ядро фрезерования и рассчитанный trace. SINUMERIK ISO Dialect T не поддерживается.

| Нативная функция | Текущее поведение |
| --- | --- |
| `G0/G1`, `G2/G3`, `G17/G18/G19`, `CR=` | Позиционирование XYZ и дуги в выбранной плоскости; отрицательный `CR` задаёт большую дугу |
| `G90/G91`, `G54`–`G59` | Абсолютные/приращённые координаты и рабочие смещения |
| `G70/G71` | Длины в дюймах/мм; единицы подачи не меняются |
| `G700/G710` | Длины и подача в дюймах/мм; числовое модальное F сохраняется |
| `G93` | Обратное время: каждое движение подачи занимает 1/F минуты, включая вращение под TCP. F должно быть положительным; при переключении G93/G94/G95 задайте новое F. Циклы и коррекция радиуса под G93 не поддержаны |
| `G40/G41/G42` | Моделируемая радиусная компенсация по настроенному инструменту |
| `DIAMON/DIAMOF/DIAM90` | Только предупреждение; все координаты исполняются в семантике DIAMOF |
| `CHF/CHR/RND/RNDM/FRC/FRCM` | Распознаются с предупреждением без изменения геометрии/подачи. Фаски, скругления и подача на переходах не моделируются. RNDM=0 распознаётся без геометрического эффекта; экспорт рассчитанной NC-программы отклоняется |
| `G60/G64` | Точный останов / непрерывное движение как метаданные; разгон, время останова и сглаживание не моделируются |
| `G500` | Модальное отключение рабочего смещения с пересчётом координат; G500/базовый фрейм по умолчанию нулевые, API `wcs_offsets[500]` позволяет задать смещение; OEM-повороты, отражения и масштабирование базового фрейма не моделируются |
| `DEF REAL`, прямые присваивания скаляров | Принимаются ограниченные скаляры `DEF REAL` с именами, начинающимися с подчёркивания, используемые в CAM-заголовках, и прямые присваивания скалярных значений |
| `T`, `M6`, `D0..D12`, `S`, базовые M-команды | Смена инструмента, выбор/отмена моделируемой режущей кромки, сигналы шпинделя и СОЖ; таблицы коррекций контроллера не моделируются |
| Именованные инструменты с `M6` | Смена именованных инструментов принимается; если геометрия фрезы неизвестна, `G41/G42` остаётся непроверенным, а радиус не подставляется автоматически |
| `G0 SUPA ... D0` | Немодальное абсолютное перемещение XYZ и настроенных A/B/C, независимо от G91. В модели приложения нулевые XYZ-адреса используют настроенную позицию возврата G28/SUPA, как FANUC G53. WCS и текущий поворотный кадр определяют отображение возврата. Нулевые поворотные адреса означают A/B/C=0; для `SUPA G0 B0 C0 D0` нужен совместимый профиль BC |
| `G64`, `MSG(...)`, `WORKPIECE(...)`, комментарии `;` | Метаданные и комментарии; сглаживание траектории и геометрия заготовки по этим объявлениям не рассчитываются |
| `SETMS(1)`, `FNORM`, `COMPOF`, `CYCLE832` | Принимаются как CAM-команды настройки/управления; `CYCLE832` игнорируется без геометрии и событий отображения |
| `MCALL CYCLE81/82/83/84(...)` | Модальное сверление/нарезание резьбы по Z в `G17/G40`, запускаемое последующими кадрами XY; отдельный `MCALL` отменяет цикл |
| `CYCLE81/82` | Сверление и быстрый возврат, выдержка в секундах для `CYCLE82`; безопасная плоскость `RFP + SDIS`, возврат на `RTP`; принимается также четырёхпараметрическая форма `CYCLE81` |
| `CYCLE83` | Первая глубина, уменьшение шага на заданную величину, минимальный шаг, дробление стружки/полный отвод и зазор повторного подхода в пределах реализованных параметров |
| `CYCLE84` | Правая метрическая резьба за один проход в `G94`: положительный явный `PIT`, `_PITA=0/1`, `SDAC=3`, ось Z, положительный `SST`, равный заданному `S`; `SST1` равен ему либо нулевой/пропущен. Подача = шаг × обороты; возврат на подаче до `RFP+SDIS`, затем быстрый ход до `RTP`, возможна выдержка в секундах |
| `TRAORI` / `TRAFOOF` | GUI/CLI/kernel TCP через общее ядро наклонных столов AC/BC; G0/G1/G2/G3 с числовыми A/B/C и прямыми R-ссылками; IC поддержан; `DC` выбирает кратчайший подход к абсолютному поворотному углу, а неоднозначность ровно 180° отклоняется |
| `CYCLE800` | GUI/CLI/kernel статические фреймы: режимы 57/54/39/27/30/45, ST200000/200001/220000/220001, DIR-1/0/1; принимается старый 15-параметрический вызов ST0/R_DATA; сброс активного фрейма пустым вызовом, bare-командой или TC="0" |

Радиусные дуги CR требуют документа SINUMERIK: используйте .mpf/.spf. В .nc или несохранённом документе действует синтаксис FANUC, который не понимает CR= как native-адрес радиуса. Native X/Y/Z=IC(...) задаёт приращение независимо от G90/G91. MSG() принимается.

`CYCLE84` принимает вызов CAM с 24 параметрами и сокращённые числовые объявления. В режиме совместимости глубина задаётся через `DP` или положительный относительный `DPR`; явный абсолютный режим `AMODE=2/1001002` требует `DP`. Глубокая резьба с дроблением/отводом, `MPIT`/таблицы резьб, неметрические единицы шага, ориентация шпинделя и технологические опции, левая резьба и разные обороты врезания/возврата пока отклоняются с диагностикой. Синхронизация и реверс представлены логическими сигналами без моделирования углового положения шпинделя. Параметры сверены с [документацией Siemens, раздел 1.7](https://m3.tuc.gr/EQUIPMENT/CTX310/840D%20G-CODE.pdf); пара `tapping_sin840d.mpf` / `tapping_fanuc.nc` проверяет геометрию G84 и повторное исполнение экспортированного trace.

Cython ускоряет последовательные участки обычных числовых кадров позиционирования; capability gate проверяет каждый кадр до изменения состояния. Нативные декларации и переключения G290/G291 прерывают только текущий участок, после чего ускорение возобновляется на подходящих кадрах. Координаты при активном цикле MCALL исполняются через Python до отмены цикла. Наличие метаданных или нативного цикла в другом месте файла не отключает ускорение всей программы.

Поддержаны числовые присваивания R-параметров (`R1=500`) и прямые ссылки `F/S/XYZ/IJK=Rn`, `CR=Rn`, `TURN=Rn`, а также ссылки в параметрах реализованных циклов. Состояние Siemens R отделено от FANUC `#` и создаётся заново для каждого исполнения. Неопределённая ссылка останавливает кадр до изменения состояния; параметры циклов проверяются при объявлении и на каждом отверстии. Арифметика `R1=R2+10` / `F=R1*0.8`, массивы, системные переменные, управляющие конструкции Siemens и произвольные вызовы подпрограмм остаются неподдержанными. Распознавание SPF не включает исполнение подпрограмм.

Нативный `TURN=n` добавляет целое число 0..999 полных оборотов к основной дуге `G2/G3` с IJK или CR, при G40 и без активного MCALL — согласно [Siemens](https://support.industry.siemens.com/cs/attachments/104985512/802Dsl_BPF_1006_en.pdf). В trace остаётся один аналитический объект дуги/спирали с полным углом. Отрисовка, playback и статистика учитывают все витки; DXF сохраняет их полилинией, FANUC/ISO делят дугу только при сериализации. Существующая модель снятия материала stock работает для точения; фрезерное снятие материала в этом релизе не добавляется. Отдельный нативный `G4 F...` задаёт секунды и не меняет модальную подачу; выдержка в оборотах шпинделя пока не моделируется.

GUI/CLI/kernel поддерживает ограниченный TCP subset TRAORI/TRAFOOF для `5ax_table_ac_angled` и `5ax_table_bc_angled`. Числовые A/B/C и прямые R-ссылки для настроенных осей следуют G90/G91; IC(число/прямая R-ссылка) всегда задаёт приращение. TCP-дуги сохраняют аналитическую XYZ-геометрию и ориентации начала/конца. CYCLE800 строит матрицу по правилам Siemens и использует общий TWP solver и ребазирование. FR0/1/2 фиксируются как запросы отвода без моделирования OEM-траектории; FR_I должен быть нулевым/пустым, поддержан DMODE0/1. DIR выбирает ветвь по знаку главного угла первого шарнира стола. ORI*, TRANS/AROT, FGROUP, FL[], FGREF[], SPOS, CUT3DC/CUT3DF/CUT3DFF и расширенные режимы управления движением принимаются с предупреждением: их эффекты не моделируются. G505–G599 не выбирают новое смещение; текущая WCS сохраняется. Конвертация такой непроверенной геометрии в NC отклоняется. Произвольные вызовы подпрограмм остаются fail-closed. G290/G291 при активном TWP/TCP отклоняются. Native MCALL и G41/G42 нельзя активировать под TCP; активный MCALL нужно отменить перед поворотным позиционированием. GUI сохраняет выбранную кинематику MPF/SPF и передаёт её общему ядру. Встроенные многоосевые посты реконструируют настроенное индексирование A/B/C, проверенное непрерывное движение `4ax_table_c` и поддержанный AC/BC TCP subset между FANUC и SINUMERIK; экспорт наклонных плоскостей/CYCLE800 остаётся fail-closed.

Профили EXPANDED проверяются повторным исполнением в тестах: сравниваются геометрия, подачи и машинные сигналы. FULL сохраняет диалект исходника.

В режиме `G291` принимаются распространённые целочисленные фрезерные G-коды, выбор единиц, системы координат, отдельные циклы и `G50/G51`. Расширенные рабочие смещения задаются через `G54 P1..P48`; исходные `G54.1` и другие дробные G-коды отклоняются, хотя `G54 Pn` внутри нормализуется в форму `G54.1 Pn` для ядра фрезерования. Обычное инкрементальное позиционирование `G91` поддерживается. `G68` ограничен отдельным 2D-блоком при активном `G90`; допускаются только центр в осях активной плоскости и `R`, без `I/J/K`. Инкрементальный угол и 3D-вектор не поддерживаются. `G69` поддерживается. Поток Macro B и неподдерживаемые функции ISO приводят к диагностике. Для `G51` используется моделируемый вес `P/1000`; альтернативные веса из параметров конкретного станка не моделируются.

`G290` выбирает нативное подмножество выше, `G291` — ISO-M. Переключатели должны находиться в отдельных кадрах. Перед `G291` отмените нативную радиусную компенсацию и `MCALL`; перед `G290` — несовместимые ISO-циклы, преобразования и расширенные смещения.

### Как определяется формат MPF и SPF?

Фильтры открытия и сохранения GUI включают `.mpf` и `.spf`. CLI и пакетный сканер по умолчанию включают эти расширения и выбирают SINUMERIK для любого `.mpf`/`.spf` независимо от содержимого; исполнение начинается в нативном режиме и обрабатывает отдельные переключатели `G290/G291`. Для анализа фрезерования укажите `--lang fanuc_mill`; этот параметр выбирает геометрическую модель фрезерования и не включает полную поддержку Siemens. Для смешанных каталогов набор файлов можно ограничить через `--extensions`.

### Можно ли конвертировать фрезерную программу FANUC в SINUMERIK?

Да. Выберите **EXPANDED EXECUTION** и целевую стойку. Постпроцессор берёт рассчитанную геометрию ядра; `sinumerik_iso` выводит ISO-M с G291, `sinumerik_840d` — native с G290.

```powershell
.\easy_gcode_plot_cli.exe export fanuc_part.nc --lang fanuc_mill --mode expanded --post-profile app\gcode\export\posts\sinumerik_iso.json -o iso_part.mpf
```

### Можно ли конвертировать SINUMERIK native в FANUC milling?

Да. Параметры и CYCLE81/82/83/84 уже исполнены ядром; EXPANDED выводит полученные перемещения, подачи, выдержки и машинные сигналы. Поддержанные операции сверления и нарезания резьбы выводятся через шаблоны выбранного поста; параметры разрешаются ядром, а исходные определения MCALL не копируются. Трёхосевой профиль `fanuc_mill` отклоняет rotary/TCP-геометрию; `fanuc_mill_multiaxis` реконструирует настроенное индексирование A/B/C, проверенное непрерывное движение `4ax_table_c` и поддержанный AC/BC TCP subset. Наклонные плоскости/CYCLE800 и непроверенные изменения геометрии по-прежнему отклоняются.

```powershell
.\easy_gcode_plot_cli.exe export native_part.mpf --lang fanuc_mill --mode expanded --post-profile app\gcode\export\posts\fanuc_mill.json -o fanuc_part.nc
```

### Чем отличаются Full Program и Expanded Execution?

**FULL** отвечает на задачу «сохранить эту программу для той же стойки, но безопасно нормализовать её». Обычная структура исходника и исходный диалект сохраняются; раскрываются только конструкции потока выполнения, которые нельзя безопасно оставить при перенумерации.

**EXPANDED** отвечает на задачу «вывести рассчитанное исполнение для выбранной стойки». Геометрия и состояния сериализуются единым движком через JSON-профиль. Трёхосевые профили остаются XYZ-only; встроенные многоосевые профили дополнительно реконструируют проверенные rotary/TCP subsets. Физические XYZ используют G54 с нулевыми смещениями; поддержанные фрезерные операции сверления и нарезания резьбы выводятся через шаблоны циклов поста, если их можно представить без изменения исполнения. Остальные операции сохраняют рассчитанные движения; макропеременные и вызовы подпрограмм заново не создаются.

```powershell
.\easy_gcode_plot_cli.exe batch-export C:\Fanuc --lang fanuc_mill --mode expanded --post-profile app\gcode\export\posts\sinumerik_iso.json -o C:\SiemensISO
.\easy_gcode_plot_cli.exe export native_part.mpf --lang fanuc_mill --mode full -o normalized.mpf
```

GUI и CLI используют одно разделение FULL / EXPANDED / DXF. Целевая стойка относится к EXPANDED. Трёхосевые посты отклоняют rotary/TCP-геометрию, а встроенные многоосевые посты реконструируют настроенное индексирование A/B/C, проверенное непрерывное движение `4ax_table_c` и поддержанный AC/BC TCP. Экспорт наклонных плоскостей/CYCLE800 остаётся fail-closed. Сам по себе выбранный профиль кинематики не превращает XYZ-программу в многоосевую. DXF — отдельный геометрический вывод без NC-постпрофиля.

### Поддерживается ли токарный SINUMERIK?

**Нет. SINUMERIK lathe / токарный SINUMERIK пока не поддерживается** — ни native, ни ISO Dialect T. Исполнение токарных Siemens-программ и конвертация в/из токарного FANUC недоступны. Описанная здесь поддержка SINUMERIK относится к фрезерованию; поддерживаемое токарное ядро FANUC — отдельный режим.

## CLI

### Использует ли CLI то же ядро, что и GUI?

Да.

Автономный CLI — это интерфейс над теми же модулями парсера, среды выполнения Macro B, машинного выполнения, циклов, компенсации и экспорта.

### Какие команды существуют?

Текущие команды:

```text
parse
trace
analyze
batch
export
batch-export
```

### Что делает `parse`?

`parse` выполняет одну программу через обычное ядро и выводит читаемую сводку инструкций, движений и диагностики.

Пример:

```powershell
.\easy_gcode_plot_cli.exe parse program.nc --lang fanuc_turn
```

### Что делает `trace`?

Пути JSON и HTML должны отличаться от исходной УП и друг от друга, включая ссылки на один файл. Совпадения отклоняются до записи. Ошибки чтения, кодировки и записи возвращают код 2 с сообщением. JSON записывается атомарно. Экспорт программы и Tool List из GUI также запрещает использовать открытую УП как файл назначения; для сохранения изменений исходника используйте Save/Save As.

`trace` выполняет одну программу и может записать подробный JSON, включая рассчитанные движения.

```powershell
.\easy_gcode_plot_cli.exe trace program.nc --lang fanuc_turn -o trace.json
```

### Что делает `analyze`?

Экспортированный HTML-отчёт всегда светлый. Окно Statistics следует теме приложения. Экспорт отчёта и программы из GUI показывает уведомление об успехе или ошибке записи. Tail-подсветка выделяет текущий логический кадр, включая все сегменты дуги, цветом текущего движения из Options; она работает при движении ползунка назад и при проигрывании Stock Removal.

`analyze` выполняет одну программу и выводит статистику траектории и диагностику. С `-o` он записывает JSON анализа.

```powershell
.\easy_gcode_plot_cli.exe analyze program.nc --lang fanuc_mill -o analysis.json
```

### Что делает `batch`?

`batch` анализирует каждый обнаруженный файл NC в каталоге и записывает отчёты JSON/CSV.

Добавьте `--html C:\Reports\html`, чтобы сохранить отдельный отчёт статистики с выбором инструмента и статичной SVG-проекцией XY/XZ для каждого файла через тот же API, что одиночный `analyze`. Подкаталоги и полные имена сохраняются; `--inches` меняет единицы отчёта. Без `--lang` расширения `.mpf/.spf` выбирают фрезерный SINUMERIK, остальные файлы сохраняют токарный режим по умолчанию. Явный `--lang` задаёт режим для всей папки.

```powershell
.\easy_gcode_plot_cli.exe batch C:\Programs --lang fanuc_mill -o C:\Reports
```

### Что делает `export`?

`export` выполняет один файл и отправляет его через общую службу экспорта NC/DXF.

```powershell
.\easy_gcode_plot_cli.exe export program.nc --lang fanuc_turn -o expanded.nc
```

### Что делает `batch-export`?

`batch-export` обнаруживает дерево каталогов и вызывает ту же службу экспорта одного файла для каждой входной программы.

Для индексированных программ A/B выберите профиль с `--kinematics PROFILE_ID`, когда все файлы используют один станок, или передайте `--kinematics-map profiles.json` для разных станков. И `batch`, и `batch-export` принимают эту карту. Это объект JSON с путями относительно входного каталога и идентификаторами профилей, например `{"a.nc":"4ax_table_a","sub/b.nc":"4ax_table_b"}`. Без профиля выполнение завершается с `ROTARY_KINEMATICS_REQUIRED`. Для EXPANDED с поворотными осями нужен многоосевой целевой пост; геометрия, которую нельзя реконструировать, отклоняется. FULL сохраняет исходные поворотные команды и применяет поддержанную текстовую нормализацию. DXF использует рассчитанную геометрию и выбранный профиль.

```powershell
.\easy_gcode_plot_cli.exe batch-export C:\Programs --lang fanuc_mill -o C:\Normalized
```

### Являются ли одиночный экспорт и пакетный экспорт разными экспортёрами?

Нет. Они используют один и тот же `ExportRequest`, проверку и конвейер `export_file()`.

Экспорт каталога — это оркестрация вокруг службы одного файла.

### Какие имена диалектов используются?

```text
fanuc_turn
fanuc_mill
```

Отдельного значения `sinumerik` для `--lang` нет. Контейнер MPF/SPF определяется по расширению независимо от содержимого, после чего для фрезерной модели указывается `--lang fanuc_mill`.

### Какие коды выхода?

Нормальное успешное/приемлемое выполнение CLI возвращает ноль. Неудачное/неполное одиночное выполнение, пакетные `ERRORS`, пакетные `NO_FILES` и ошибки экспорта возвращают ненулевой код (в настоящее время 2 для ошибок уровня команды).

### Как увидеть все параметры и значения по умолчанию?

Используйте:

```powershell
.\easy_gcode_plot_cli.exe --help
```

или справку по конкретной команде, например:

```powershell
.\easy_gcode_plot_cli.exe batch-export --help
```

Справка верхнего уровня также выводит разделы справки подкоманд.

## Пакетный анализ

### Что проверяет пакетный анализ?

Каждый найденный файл анализируется тем же способом, что и при одиночной команде `analyze`.

Отчёты по файлам включают:

- статус;
- `ok` / `complete`;
- размер файла и количество строк;
- количество движений;
- количество выполненных блоков;
- количество диагностик;
- неподдерживаемые G-коды;
- неподдерживаемые M-коды;
- полные записи диагностики;
- прошедшее время.

### Какие статусы пакета существуют?

```text
CLEAN
WARNINGS
ERRORS
NO_FILES
```

`CLEAN` означает, что диагностика не выдавалась.

`WARNINGS` означает, что выполнение допустимо/полно, но диагностика остаётся.

`ERRORS` означает, что хотя бы один файл недопустим/неполон или содержит диагностику уровня ошибки.

`NO_FILES` означает, что обнаружение не нашло подходящих программ.

### Какие расширения сканируются по умолчанию?

```text
.nc
.cnc
.ptp
.mpf
.spf
.tap
.txt
```

Сканирование рекурсивное, если не указан `--top-level-only`.

### Могут ли быть обнаружены файлы без обычного расширения NC?

Да, когда используется набор расширений по умолчанию. Сканер также распознаёт вероятные текстовые программы ЧПУ, в начале которых обнаруживается заголовок O-программы или несколько блоков с G/M-кодами.

Файлы, определённые как бинарные, не рассматриваются как текст NC.

### Детерминировано ли обнаружение?

Да. Пути сортируются по нормализованному относительному пути, поэтому порядок отчёта не зависит от порядка перечисления файловой системы.

### Можно ли ограничить расширения?

Да:

```powershell
--extensions .nc,.tap
```

Когда задан пользовательский набор расширений, обнаружение по содержимому произвольных имён файлов намеренно не используется.

### Какие данные сводятся в итоговый отчёт?

Отчёт агрегирует:

- количество статусов файлов;
- общее количество диагностик;
- общие суммы ошибок и предупреждений;
- частоты кодов диагностики;
- количество вхождений/файлов неподдерживаемых G-кодов;
- количество вхождений/файлов неподдерживаемых M-кодов;
- общее прошедшее время.

### Какие файлы записываются?

Имена отчётов по умолчанию:

```text
batch_report.json
batch_report.csv
```

CSV — UTF-8 с BOM для удобного открытия в электронных таблицах.

### Останавливает ли плохой входной файл весь пакет?

Ошибка чтения/декодирования становится `FILE_PROCESSING_ERROR` для файла, и обработка продолжается.

Неожиданные внутренние сбои анализатора намеренно не проглатываются как поддельная пользовательская диагностика. Регрессии программирования должны оставаться видимыми.

### Существуют ли предустановленные пакетные скрипты?

Отдельных предустановленных скриптов для обычного `batch`-анализа больше нет. Запускайте CLI напрямую, явно задавая исходный каталог и каталог отчёта.

## Пакетный экспорт

### Какую проблему решает пакетный экспорт?

`batch-export` применяет один проверенный контракт экспорта ко всему дереву каталогов.

Типичные применения включают:

- раскрытие выполнения;
- нормализацию номеров последовательности;
- добавление/удаление пробелов;
- удаление комментариев;
- преобразование единиц поддерживаемых программ между мм и дюймами;
- изменение представления дуг фрезерования;
- генерацию каталога траекторий DXF.

### Изменяет ли пакетный экспорт входные файлы?

Нет. Выходной каталог должен быть отдельным каталогом.

Выходной каталог не может быть входным каталогом или его дочерним каталогом, что предотвращает рекурсивную самообработку.

### Сохраняется ли иерархия исходных каталогов?

Да.

Пример:

```text
input/
  part1.nc
  machine_a/
    part2.tap
```

Вывод NC становится:

```text
output/
  part1.nc
  machine_a/
    part2.nc
```

Вывод DXF использует `.dxf`.

### Что происходит, если два исходных имени отображаются в одно выходное имя?

Пакет отклоняется до записи неоднозначных выходных данных. Например, два соседних входных файла, разные расширения которых оба станут одним и тем же местом назначения `.nc`, обнаруживаются как коллизия.

### Останавливает ли одна ошибка экспорта все файлы?

Обычные ошибки чтения/экспорта/значения для файла становятся записью `ERRORS`, и обработка продолжается.

Успешно выполненный файл с диагностикой экспортируется и помечается `WARNINGS` в соответствии с текущей политикой.

Выполнение, которое не является `ok` или не является `complete`, не создаёт выходной файл.

### Какие файлы описывают пакетный экспорт?

Корень вывода содержит:

```text
batch_export_report.json
batch_export_report.csv
```

Манифест включает относительные пути исходных/выходных файлов, статус, количество движений, количество выполнений, диагностику, эффективные выходные единицы, эффективный тип дуги фрезерования и прошедшее время.

### Какие статусы batch-export?

По файлу:

```text
EXPORTED
WARNINGS
UNSUPPORTED
ERRORS
```

В целом:

```text
CLEAN
WARNINGS
UNSUPPORTED
ERRORS
NO_FILES
```

### Какие режимы экспорта доступны из CLI?

Для NC есть два режима:

```text
expanded
full
```

DXF выбирается через `--format dxf`; параметры режима/форматирования, относящиеся только к NC, отклоняются при явной передаче.

### Какие параметры намеренно отклоняются в режиме Full Program?

Full Program не принимает явные:

- преобразование единиц, отличное от `auto`;
- выбор типа дуги;
- преобразование режима координат;
- управление модальной подачей.

Это сделано, чтобы не создавать ложного впечатления, будто такие преобразования семантически эквивалентны Expanded Execution. Параметры строки безопасности, текста начала/конца программы, нумерации кадров, разделителя и ведущего нуля FULL применяет, потому что они меняют оформление текста, а не геометрию.

### Можно ли задать начальный номер последовательности/приращение без номеров последовательности?

Нет. Явное начало, приращение или интервал последовательности требуют `--sequence-numbers`.

### Существуют ли предустановленные скрипты batch-export?

Да. В дереве разработки есть четыре конкретные проверки EXPANDED-конвертации для Windows и Linux:

```text
fanuc_mill_to_sinumerik_native
fanuc_mill_to_sinumerik_iso
fanuc_lathe_a_to_b
sinumerik_native_to_fanuc_mill
```

Они запускают собранный CLI с явным JSON-постпрофилем и пишут результат в `tmp/test_export`. Приложение они не пересобирают.

## Конфигурация

### Где хранится конфигурация приложения в Windows?

```text
%LOCALAPPDATA%\easy-gcode-plot\config.ini
%LOCALAPPDATA%\easy-gcode-plot\tools.db
```

Сниппеты используют собственное хранилище SQLite в Local AppData.

### Что хранится в `config.ini`?

Настройки приложения/UI включают, например:

- язык;
- тему;
- кодировку документа;
- настройки редактора;
- Auto Update;
- максимальное количество сгенерированных движений;
- параметры компенсации;
- допуск дуги и автоопределение дуг фрезерования;
- поведение Block Skip;
- цвета графика и отображение геометрии;
- настройки заготовки;
- скорость воспроизведения;
- горячие клавиши;
- стиль комментариев.

### Можно ли заменить `tools.db` старыми значениями JSON в config.ini?

Нет. Основной источник данных об инструментах — `tools.db`. Устаревший JSON в конфигурации не используется для записи изменений в текущую базу.

### Где находится файл журнала?

Когда логирование включено:

```text
%LOCALAPPDATA%\easy-gcode-plot\main.log
```

### Что добавляет логирование DEBUG?

Логирование DEBUG включает дополнительную информацию о выполнении, рендеринге, камере, параметрах и времени Stock Removal. Медленные кадры заготовки ограничиваются по частоте, чтобы логирование не создавало ещё более серьёзную проблему производительности.

## Устранение неполадок

### График пуст

Проверьте:

- выбранный режим станка;
- диагностику выполнения;
- конфигурацию WCS/домашней позиции;
- содержит ли программа поддерживаемое движение;
- не оставил ли предыдущий неподдерживаемый блок, изменяющий позицию, позицию неизвестной.

### Движение Macro B отсутствует

Проверьте первую диагностику. Распространённые причины включают:

- неопределённую переменную;
- отсутствующую метку GOTO;
- отсутствующую цель O-программы;
- несогласованный WHILE/END;
- ошибку аргумента G65;
- ограничение глубины вызовов/ресурсов.

Используйте Tokens/Macro Variables, чтобы проверить состояние при соответствующем выполнении блока.

### Мои слова G65 M/S/T не запустили шпиндель/СОЖ/смену инструмента

Это сделано намеренно. В блоке G65 эти слова служат аргументами макроса, а не командами управления станком.

### Компенсация фрезы не видна

Убедитесь, что:

- G41/G42 активен;
- выбранный инструмент обнаружен или настроен;
- его геометрия допустима;
- тип контура поддерживается.

Проверьте диагностику на состояние компенсации `UNVERIFIED`.

### G43 присутствует в исходном коде, но отображаемый Z не включает длину инструмента

G43/G49 и H отслеживаются, но смещение длины инструмента пока не применяется к рассчитанной траектории.

### G71 оставляет материал не с той стороны

Проверьте знак припуска U второй строки и является ли контур наружным или внутренним. Проект намеренно сохраняет семантику знакового U.

### G72 Type II сообщает об ошибке

Плоскость торцевой обработки может содержать несколько несвязных диапазонов профиля, точный выбор которых зависит от контроллера. Такой случай отклоняется как `UNSUPPORTED_G72_TYPE_II_SPANS`, а не угадывается.

### G76 сообщает `UNSUPPORTED_G76_TOOL_ANGLE`

Упакованный угол P в настоящее время должен быть одним из:

```text
0, 29, 30, 55, 60, 80
```

### Пакет показывает `UNSUPPORTED_M_CODE`, но геометрия выглядит правильно

Действие этого M-кода на станок не моделируется. Пакетный анализ сохраняет рассчитанную траекторию и предупреждает, что полное поведение реального станка не проверено.

### Преобразование единиц экспорта отклонено

EXPANDED преобразует единицы по рассчитанной геометрии/состояниям, а не масштабирует исходный текст. Если экспорт отклонён, смотрите конкретную диагностику выполнения/постпроцессора (например, неподдерживаемая TWP/CYCLE800 или иная непроверенная геометрия, либо неполное выполнение). FULL намеренно поддерживает только `--units auto`.

### Batch-export сообщает, что выходной каталог недействителен

Корень вывода должен находиться вне дерева входного каталога. Это предотвращает обнаружение и повторный экспорт экспортированных файлов во время того же запуска.

### Большая программа не обновляется во время набора

Используйте Refresh. Auto Update не перестраивает траекторию при каждой правке, если превышен заданный порог дискретизации.

### GUI сообщает, что текущее выполнение устарело

Текст редактора изменился после создания отображаемого `ExecutionResult`. Обновите перед использованием информации, зависящей от выполнения, такой как Macro Variables или экспорт.

## Разработка и архитектура

### Как организовано ядро ЧПУ?

Важные пакеты:

```text
app/gcode/kernel/api/
app/gcode/kernel/frontend/
app/gcode/kernel/geometry/
app/gcode/kernel/runtime/
app/gcode/kernel/turning/cycles/
app/gcode/kernel/milling/
app/gcode/kernel/milling/cycles/
app/gcode/kernel/compensation/
```

### Что относится к `frontend/`?

Frontend владеет:

- удалением комментариев;
- лексированием слов;
- выражениями с учётом Macro B;
- разбором узлов потока;
- исходными блоками;
- построением AST/модели;
- ускорением нативного парсера.

Лексер учитывает скобки, поэтому имена функций Macro B и `GOTO` не читаются ошибочно как адресные слова ЧПУ.

### Что относится к `runtime/`?

Runtime владеет общими механизмами выполнения, такими как:

- поток Macro;
- локальная область G65;
- диспетчеризация M98/M99;
- проверка модальных групп;
- сигналы и структурные события;
- контракты циклов;
- ограничения ресурсов;
- построение трассы точения;
- оркестрация раскрытия циклов.

### Почему циклы точения — отдельные файлы?

Каждый крупный цикл имеет сфокусированную реализацию в `turning/cycles/`, в то время как общие механизмы диспетчеризации/раскрытия находятся в runtime. Это позволяет тестировать геометрию G70-G76 без построения одной монолитной функции интерпретатора.

### Что относится к `milling/`?

Состояние фрезерования, выполнение движения, полярное программирование и выполнение циклов находятся в пакете milling. Нативное выполнение фрезерования ускоряет выбранные пути движения без создания другой семантики.

### Что относится к `compensation/`?

Компенсация радиуса вершины токарного резца и радиуса фрезы рассчитывается по уже определённым движениям.

Они не относятся к рендереру OpenGL.

### Что относится к `app/gcode/export/`?

Пакет намеренно небольшой:

- `common.py` — общие параметры, форматирование движений и масштабирование единиц;
- `full.py` — FULL-нормализация исходника по исходному тексту и карте исполнения;
- `expanded.py` — единый JSON-постпроцессор рассчитанной геометрии/состояний;
- `dxf.py` — геометрический DXF;
- `posts/*.json` — пять встроенных профилей стоек.

Оркестрация одиночного CLI-экспорта находится в `app/gcode/export_file.py`; `batch_export.py` применяет тот же контракт к дереву каталогов. Второго интерпретатора G-кода в экспорте нет.

### Что делает `program_execution.py`?

Это общий путь настройки приложения, используемый для выполнения программы с тем же обнаружением инструментов и конфигурацией ядра, что и рабочие процессы GUI/CLI.

### Что делает `batch.py`?

Он находит файлы по заданным правилам и для каждого запускает общее ядро, чтобы построить отчёты анализа. Отдельного анализатора G-кода в нём нет.

### Что делает `batch_export.py`?

Это оркестрация каталога вокруг той же службы `export_file()`, используемой одиночным экспортом CLI.

### Какие нативные компоненты существуют?

Проект собирает нативные расширения для:

- разбора frontend;
- выбранных путей выполнения фрезерования;
- обнаружения инструментов.

Основой остаётся контракт Python. Регрессионные тесты проверяют совпадение нативной реализации и Python. `app.native` кэширует доступность parser/discovery/executor и причины ошибок импорта. Source-запуск допускает fallback; frozen-релиз требует все три расширения и явно отказывает при отсутствии расширения или ошибке загрузки DLL. Runtime build и установка зависимостей не выполняются.

`parser_statistics()` показывает total/native/fallback blocks последнего успешного разбора в текущем контексте по фактическим fallback callbacks. Необычные разделители строк и слишком длинные числовые слова используют reference parser для сохранения parity. Обычные LF/CRLF-программы сохраняют native scanner.

CLI parse/trace/analyze/batch не загружают ezdxf. DXF backend импортируется только при DXF export; его отсутствие даёт контролируемую ошибку экспорта.

### Как публично представлены результаты выполнения?

Основные неизменяемые публичные типы включают:

- `Diagnostic`;
- `SemanticInstruction`;
- `TraceMotion`;
- `ArcGeometry`;
- `MachineSignal`;
- `ExecutionEvent`;
- `ExecutionStep`;
- `ExecutionResult`.

### Что такое `ExecutionStep`?

Ядро не импортирует Qt: пути пользовательских профилей определяет `app.paths`, а GUI-настройки остаются в `app.settings`. Парсер и выполнение не меняют глобальные настройки сборщика мусора; бюджеты выполнения привязаны к контексту вызова.

Источником данных являются разобранные блоки. Cython строит ProgramAst и обе таблицы меток за один проход; Python-путь даёт тот же результат. Внутренний путь parser не строит AST повторно, публичный конструктор проверяет соответствие блокам. Используется ограниченный локальный кэш неизменяемых слов. Глобальное состояние GC не меняется. Относительные проверки: `pytest tests/core/test_ast_acceleration.py -m performance`.

JSON-отчёты записывают `kinematics_definition` и `kinematics_fingerprint` (SHA-256) фактически использованного профиля, включая нормализованные оси стола/головы и их порядок. CSV содержит то же определение в формате JSON. Один ID профиля не гарантирует одинаковый расчёт при разных пользовательских overrides; отчёт не перечитывает каталог после выполнения.

Он записывает одно выполненное появление исходного блока и включает информацию, такую как:

- индекс исходного блока;
- количество выданных движений;
- масштаб единиц;
- режим диаметра/радиуса;
- состояние абсолютного/инкрементального;
- вычисленные слова;
- сигналы;
- позиция;
- активный WCS;
- состояние подачи/шпинделя;
- снимок переменных Macro B;
- события выполнения.

Эта модель уровня появления необходима для циклов и подпрограмм, где одна строка исходного кода выполняется несколько раз.

### Что такое `ExecutionEvent`?

События описывают структурные факты, которые не являются обычной геометрией, включая границы программы/подпрограммы, смены инструмента и возвраты в референсную точку.

Поэтому экспорт может сохранять структурный порядок выполнения без реконструкции из геометрии движения.

### Как запустить ежедневный GUI smoke-тест с видимым окном?

Готовые скрипты настраивают окружение автоматически: `scripts\ps1\start-sandbox.ps1` для Windows или `bash scripts/sh/start-sandbox.sh` для Linux/macOS. По умолчанию запускается визуальное demo. Для режима offscreen используйте `-Automated` / `--automated`, для темпа демонстрации — `-DelayMs 1500` / `--delay-ms 1500`. PowerShell-скрипт восстанавливает прежние переменные окружения; Bash-скрипт задаёт их только дочернему процессу.

Обычный автоматический sandbox запускается из корня репозитория в PowerShell:

```powershell
.\scripts\ps1\test.ps1 tests/gui/test_daily_workflow_smoke.py -q -s
```

Для визуального demo с паузами включите платформу Windows и режим демонстрации:

```powershell
$env:QT_QPA_PLATFORM = "windows"
$env:EASY_GCODE_SMOKE_DEMO = "1"
try {
    .\scripts\ps1\test.ps1 tests/gui/test_daily_workflow_smoke.py -q -s
}
finally {
    Remove-Item Env:QT_QPA_PLATFORM -ErrorAction SilentlyContinue
    Remove-Item Env:EASY_GCODE_SMOKE_DEMO -ErrorAction SilentlyContinue
}
```

Одна переменная `QT_QPA_PLATFORM=windows` показывает окно, но не включает паузы и итоговый demo-диалог. По умолчанию `EASY_GCODE_SMOKE_DELAY_MS` равен 1000 мс: действия показываются 1 секунду, основные этапы и диалоги — 2 секунды, итог — 4 секунды. Темп можно изменить:

```powershell
$env:EASY_GCODE_SMOKE_DELAY_MS = "1500"
```

В обоих режимах выполняются одинаковые проверки. Используются существующие файлы без переноса или изменения:

- FANUC milling: `tests/fixtures/milling/fanuc/flange_plate_benchmark.nc`, без STL; тёмная тема, сетка/цвета и сохранение настроек, Statistics с выбором инструмента и HTML с SVG, экспорт Expanded FANUC с повторным исполнением ядром. Толщина линии сохраняется.
- FANUC turning: `tests/fixtures/turning/lathe_cycles_example.nc`; G71/G76 и настоящий Stock Removal с детерминированной перемоткой. Геометрия из библиотеки по совпадающему номеру приоритетнее автоматического распознавания.
- SINUMERIK 3+2: `tests/fixtures/milling/sinumerik/5ax_test.mpf`, `stl/test6.stl`, профиль AC. В STL Objects: Base Point Origin, Position Z=-100, Move Here.
- SINUMERIK impeller: `tests/fixtures/milling/sinumerik/impeller.mpf`, `stl/test7.stl`, профиль `5ax_table_bc_angled`. В STL Objects: Transform, поворот Z на +90°, затем Section Y на нуле, Apply, Undo, затем STL edges only. В редакторе sandbox выбирается сохранённая геометрия конической сферической фрезы T60 с D1. Короткий Play, затем переходы ползунка с шагом 10% до конца. Токарный Stock Removal и flange сохраняют полное непрерывное воспроизведение.

Pytest изолирует настройки, библиотеку инструментов и выходные файлы во временных каталогах. Фиксированный T0303 P2 находится во временной библиотеке sandbox, а не в пользовательской SQLite. Диалоги выбора файлов получают заданные пути; диалоги и действия приложения остаются настоящими. Неожиданные окна сообщений приводят к ошибке этапа вместо зависания. Проверяется состояние виджетов, модели и сцены, а не пиксели OpenGL. Оба режима печатают результаты этапов; demo также показывает итоговый диалог с таймером и указывает неуспешный этап при ошибке проверки.

Подробности этапов и платформ — в [инструкции GUI sandbox](docs/GUI_SANDBOX.md).

## Сборка и выпуск

### Как собрать в Windows?

```powershell
.\scripts\ps1\build.ps1
```

Сборка создаёт отдельные исполняемые файлы GUI и CLI плюс файлы контрольных сумм SHA-256.

### Как собрать в Linux?

```bash
bash scripts/sh/build.sh
```

Для консольной упаковки после того, как тесты уже пройдены:

```bash
bash scripts/sh/build.sh --console --skip-tests
./dist/easy_gcode_plot_cli --help
(cd dist && sha256sum -c easy_gcode_plot_cli.sha256)
```

### Использует ли проект отдельную среду сборки?

Да. Нативный/релизный инструментарий использует постоянный `.venv-build`, а не заменяет или очищает `.venv` разработчика.

Нативная сборка проверяет отслеживаемые `.pyx` и состояние зависимостей и может переиспользовать среду сборки, когда ничего relevant не изменилось.

### Как проверяются релизы в CI?

Рабочий процесс релиза запускает полный набор тестов и статические проверки в Linux и Windows до упаковки. Оба упакованных CLI проходят smoke-проверку через `--help`; Linux-архив получает SHA-256 sidecar, Windows публикует контрольные суммы GUI/CLI, а release-job скачивает оба артефакта перед созданием или обновлением GitHub Release по тегу.

### Запускается ли исполняемый файл Linux как Windows `.exe`?

Нет. Артефакты Windows и Linux — платформенно-зависимые сборки, хотя они используют одну и ту же реализацию Python/ядра и контракт CLI.
